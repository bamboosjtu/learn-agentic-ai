# LLM 可观测性与评估完整入门指南

## 介绍：我们到底想做什么？

假设你构建了一个可以回答客户问题的 AI 应用。那你怎么知道它表现得好不好？又该如何让它变得更好？这份指南会从最基础的地方开始，把这些内容一步步讲清楚。

---

## 第一部分：理解可观测性（看清你的应用在做什么）

### 什么是可观测性？

**简单定义：** 可观测性就是能够看到并理解你的 AI 应用在运行时到底做了什么。

你可以这样理解：如果你的 AI 应用像一个正在工作的员工，那么可观测性就像一个记录一切行为的监控摄像头。你可以回放过程，看看究竟发生了什么。

### 为什么我们需要可观测性？

当你向一个 AI 应用提出问题时，幕后其实发生了很多步骤：

- 应用收到你的问题
- 它可能会调用 AI 模型
- 它可能会搜索文档
- 它可能会使用工具或函数
- 最后，它给出答案

如果没有可观测性，你就像在盲飞。你只能看到最终答案，却看不到应用是如何得到这个答案的。

---

## 第 1 步：理解基础构建块

### 什么是 Run？

一个 **run** 就是你的应用执行的一个单独动作或步骤。

**例子：做一个三明治**

- 拿出面包 = 1 个 run
- 抹黄油 = 1 个 run
- 加芝士 = 1 个 run
- 把两片面包合起来 = 1 个 run

每个单独动作都可以看作一个 run。

在 AI 应用里：

- 调用一次 AI 模型 = 1 个 run
- 搜索文档一次 = 1 个 run
- 格式化一个 prompt = 1 个 run

**关键点：** run 代表应用中最小的工作单元。

---

### 什么是 Trace？

一个 **trace** 就是从开始到结束完整发生过程的记录。

**继续用三明治举例：**

- 做完整个三明治的全过程（4 个步骤加起来）= 1 个 trace
- 每个单独步骤 = 这个 trace 里的 1 个 run

在 AI 应用中：

- 用户提问 -> 应用搜索文档 -> 调用 AI 模型 -> 返回答案
- 整个过程 = 1 个 trace
- 每个箭头间的动作 = trace 中的一个 run

**关键点：** trace 是一组 runs，用来展示从输入到输出的完整路径。

---

### 什么是 Project？

一个 **project** 就是一个用来容纳多个 traces 的容器。

你可以这样理解：

- project = 一个文件柜
- traces = 文件柜里的每个文件夹
- runs = 每个文件夹里的文档

**例子：**

- 你可能有一个 “Customer Support Bot” 项目
- 里面包含每个用户问题对应的 traces
- 每个 trace 里又包含这个问题处理过程中所有的 runs

**关键点：** project 帮助你把相关 traces 组织在一起。

---

## 第 2 步：用于更好组织的附加概念

### Tags

**Tags（标签）** 是你附加到 runs 上的分类标记。

**现实类比：** 就像你给文件贴便利贴来做分类。

**例子：**

- 给高优先级请求打上 `"urgent"`
- 给西班牙语问题打上 `"spanish"`
- 给产品相关问题打上 `"product-question"`

**标签为什么重要：**

- 方便后续快速定位特定类型的 runs
- 可以按标签筛选和分析
- 有助于发现模式

---

### Metadata

**Metadata（元数据）** 是以键值对形式保存的附加信息。

你可以把它理解成快递包裹上的详情标签：

- `customer_id`: `"12345"`
- `timestamp`: `"2025-10-09 14:30"`
- `version`: `"v2.1"`
- `region`: `"north-america"`

**元数据为什么重要：**

- 为每个 run 保存上下文信息
- 按特定属性过滤 runs
- 跟踪版本和运行环境

---

### Feedback

**Feedback（反馈）** 是你给某个 run 的评分或评价。

**简单例子：** 就像给餐厅打分：

- 5 星 = 非常好
- 2 星 = 很差

**在 AI 应用里：**

- 用户点击 “thumbs up” -> 反馈分数 = 1
- 用户点击 “thumbs down” -> 反馈分数 = 0
- 或者使用数值分，如 0.85（85% 质量）

**反馈的类型：**

1. **用户反馈**：真实用户为回答打分
2. **自动反馈**：由你的代码自动给输出打分
3. **人工反馈**：你或团队成员人工审核并评分

**关键点：** 反馈能够告诉你应用表现得怎么样。

---

## 第二部分：理解评估（检查你的应用表现如何）

### 什么是评估？

**简单定义：** 评估就是测试你的 AI 应用，看看它表现得有多好。

**现实类比：**

- 构建一个应用 = 教某人一份工作
- 评估 = 给他一场考试，看看他学会了没有

### 为什么要做评估？

1. **确认是否可用**：应用真的能正确回答问题吗？
2. **定位问题**：它在哪些地方出错？
3. **衡量改进**：新版本比旧版本更好吗？
4. **建立信心**：你能放心把它投入生产吗？

---

## 第 3 步：评估的核心概念

### Datasets：你的测试集合

**Dataset（数据集）** 是一组用来测试应用的样例集合。

你可以把它理解成一份练习试卷，里面有问题和答案：

```
Question 1: What is the capital of France?
Expected Answer: Paris

Question 2: How do I reset my password?
Expected Answer: Click on 'Forgot Password' link...

```

### 一个数据集里有什么？

数据集中的每个样例通常包含：

1. **Inputs**：你给应用的问题或提示词
   - 例子：`"What are your business hours?"`
2. **Reference Outputs（可选）**：你期望的正确答案
   - 例子：`"We're open Monday-Friday, 9 AM to 5 PM"`
3. **Metadata（可选）**：关于这个样例的额外信息
   - 例子：`category: "hours"`, `difficulty: "easy"`

### 数据集为什么重要？

- **一致性**：每次都以相同方式测试应用
- **可比较性**：比较应用不同版本
- **覆盖度**：确保测试到不同类型的场景

---

### 构建你的第一个数据集

**逐步方法：**

### 方法 1：手工创建

从小规模开始。先手工做 10 到 20 个样例：

```
Example 1:
Input: "How do I return a product?"
Expected Output: "You can return products within 30 days..."
Category: "returns"

Example 2:
Input: "What payment methods do you accept?"
Expected Output: "We accept credit cards, PayPal, and..."
Category: "payment"

```

**建议重点关注：**

- 常见问题
- 边界情况（少见、特殊的场景）
- 已知容易出问题的区域

### 方法 2：使用真实数据

当你的应用开始运行后：

- 收集真实用户提问
- 选出有代表性或有问题的样例
- 把它们加入数据集

### 方法 3：合成生成

当你已经有一些样例后：

- 用 AI 生成相似样例
- 更快扩充数据集
- 生成已有样例的不同变体

---

### Evaluators：你的评分系统

**Evaluator（评估器）** 是一个函数，用来给你的应用在测试中的表现打分。

你可以把它理解成老师批改作业。评估器会看：

- 提问内容是什么（input）
- 你的应用回答了什么（output）
- 正确答案应该是什么（reference，如果有）

### 评估器的类型

**1. Heuristic Evaluators（基于规则的评估器）**

这类评估器遵循简单、固定的规则。

**例子：**

- 检查答案是否为空
- 检查答案是否包含某些关键词
- 检查答案格式是否正确
- 衡量回答长度

**代码示例（概念性）：**

```python
def check_not_empty(output):
    if len(output) > 0:
        return {"score": 1, "comment": "Answer provided"}
    else:
        return {"score": 0, "comment": "Empty answer"}

```

**适用场景：**

- 简单检查
- 快速评估
- 明确的通过/失败标准

---

**2. LLM-as-Judge Evaluators**

使用另一个 AI 模型来给输出打分。

**工作方式：**

1. 把问题和答案交给一个 AI 模型
2. 要求它根据标准评估质量
3. AI 返回分数和解释

**给 AI 评委的示例 Prompt：**

```
Question: "What are your business hours?"
Answer: "We're open every day from 9 to 5"
Reference Answer: "Monday-Friday, 9 AM to 5 PM EST"

Evaluate if the answer is factually accurate compared to the reference.
Give a score from 0-1 and explain why.

```

**适用场景：**

- 复杂问题
- 需要更细致的判断
- 需要比较“含义”而不是字面是否一致

---

**3. Human Evaluators（人工评估）**

由真实的人来审核并打分。

**流程：**

1. 向人工评审展示问题和回答
2. 让他们评价质量（点赞/点踩或 1 到 5 星）
3. 收集并分析评分

**适用场景：**

- 主观性较强的任务，人工最准确
- 刚开始时帮助理解质量问题
- 对重要改动做最终验证

---

### Experiments：测试你的应用

一个 **experiment（实验）**，就是让你的应用在整个数据集上跑一遍，并收集结果。

你可以把它理解成：给学生做一整套考试，然后看整体成绩如何。

### 一个实验里会发生什么？

1. **准备**：你有一个包含 100 个测试问题的数据集
2. **运行**：你的应用回答这 100 个问题
3. **评估**：每个答案都由评估器打分
4. **分析**：查看总体表现并定位问题

### 示例实验结果：

```
Dataset: Customer Support Questions (50 examples)
Average Score: 0.82 (82%)
- 41 questions answered correctly
- 9 questions answered incorrectly
- Common issue: Wrong information about shipping

```

## 第 4 步：评估的类型

### 离线评估

**含义：** 在部署前，使用预先准备好的测试数据来测试你的应用。

**现实类比：** 就像正式演出前的彩排。

**过程：**

1. 创建一个数据集
2. 在数据集上运行应用
3. 评估结果
4. 修复问题
5. 持续重复直到满意

**适用场景：**

- 发布新版本前
- 测试你对应用做出的修改
- 比较不同实现方案

**优点：**

- 安全，不影响真实用户
- 环境可控
- 可重复执行

**缺点：**

- 仅限于测试样例
- 可能遗漏真实世界问题

---

### 在线评估

**含义：** 在应用已经上线、面向真实用户运行时，对输出实时进行评估。

**现实类比：** 就像安保人员实时盯着监控，发现问题马上处理。

**工作方式：**

1. 用户提问
2. 应用生成回答
3. 评估器立刻检查该回答
4. 标记问题或给出分数
5. 收集反馈

**示例检查项：**

- 回答是否合适？
- 是否包含有害内容？
- 是否与问题相关？

**适用场景：**

- 监控在线应用
- 捕捉意外问题
- 理解真实世界表现

**优点：**

- 能发现真实问题
- 反馈及时
- 使用真实用户数据

**缺点：**

- 可能成本较高
- 需要足够快的评估器
- 更难调试

---

### 成对评估（Pairwise Evaluation）

**含义：** 把应用的两个不同版本放在一起做对比。

**现实类比：** 就像可乐盲测，比较 Coke 和 Pepsi 哪个更好。

**例子：**

```
Question: "What's your return policy?"

Version A Answer: "Returns accepted within 30 days with receipt."
Version B Answer: "You can return items within 30 days. Keep your receipt!"

Judge: Which answer is more helpful and friendly?
Result: Version B is better (more detailed and friendly)

```

**适用场景：**

- 比较旧版本和新版本
- 测试不同 prompt
- 在不同 AI 模型之间做选择

**为什么有用：**

- 有时比绝对打分更容易
- 人类更擅长做比较
- 能帮助你选出更优方案

## 第 5 步：常见评估场景

### 场景 1：测试答案正确性

**目标：** 检查应用是否给出了正确信息。

**你需要：**

- 一个包含问题和正确答案的数据集
- 一个能比较实际答案和期望答案的评估器

**例子：**

```
Input: "What is 2 + 2?"
Expected: "4"
Actual: "4"
Score: 1.0 (Correct!)

Input: "What is the capital of France?"
Expected: "Paris"
Actual: "The capital is Lyon"
Score: 0.0 (Wrong!)

```

---

### 场景 2：测试回答质量

**目标：** 即使没有唯一“标准答案”，也检查回答是否有帮助。

**你需要：**

- 一个问题数据集
- 一个基于质量标准的 LLM-as-Judge 评估器

**示例标准：**

- 回答是否相关？
- 是否清晰易懂？
- 是否完整？
- 语气是否合适？

---

### 场景 3：发现回归问题

**目标：** 确保新改动不会破坏以前本来工作正常的部分。

**流程：**

1. 在当前版本上运行评估（Baseline）
2. 修改应用
3. 在新版本上再次运行评估
4. 比较结果：分数是否下降？如果下降，那就是回归

**例子：**

```
Baseline Version: 90% correct answers
New Version: 75% correct answers
REGRESSION DETECTED! New version is worse.

```

---

## 第 6 步：给初学者的最佳实践

### 从小处开始

**不要这样做：** 第一天就创建 1000 个测试样例
**应该这样做：** 先从 10 到 20 个精心挑选的样例开始

**原因：**

- 更容易管理
- 迭代更快
- 更容易理解什么最重要

### 从简单评估器开始

**不要这样做：** 一上来就搭复杂的 AI 评委
**应该这样做：** 从简单检查开始：

- 响应是否为空？
- 是否包含必须的关键词？
- 长度是否合适？

**原因：**

- 更容易理解
- 执行更快
- 出错点更少

### 仔细看你的数据

**不要这样做：** 只看汇总分数
**应该这样做：** 阅读真实样例：

- 看哪些问题失败了
- 理解失败原因
- 总结模式

**原因：**

- 数字不会讲完整故事
- 你能发现真实问题
- 有助于建立更好的改进直觉

### 高频迭代

**不要这样做：** 改很多地方后再一起测试
**应该这样做：** 每次只改一处，测试，然后重复

**原因：**

- 更清楚是哪项改动带来了提升或问题
- 学得更快
- 不容易被复杂性压垮

---

## 第 7 步：把所有内容串起来

### 完整工作流

**阶段 1：初始化（做一次）**

1. 给应用加上可观测性
2. 创建一个小型初始数据集（10 到 20 个样例）
3. 定义 1 到 2 个简单评估器

**阶段 2：建立基线（做一次）**
4. 在数据集上运行当前应用
5. 查看结果和分数
6. 找出问题区域

**阶段 3：改进（循环执行）**
7. 对应用做一个改进
8. 再次运行评估
9. 与基线比较
10. 如果更好，就把它作为新的基线
11. 如果更差，就撤销改动

**阶段 4：扩展（长期进行）**
12. 往数据集里增加更多样例
13. 增加更复杂的评估器
14. 在生产环境运行在线评估
15. 使用真实用户反馈

---

## 常见错误与避免方式

### 错误 1：没有可观测性

**问题：** 你看不到应用到底做了什么
**解决方案：** 从第一天开始加 tracing

### 错误 2：样例太少

**问题：** 测试分数不能代表真实表现
**解决方案：** 逐步扩展数据集，并保证样例多样化

### 错误 3：只依赖自动评估

**问题：** 会漏掉只有人才能发现的细微问题
**解决方案：** 定期人工审核样例

### 错误 4：忽视边界情况

**问题：** 应用在特殊场景下失败
**解决方案：** 专门把边界情况加入数据集测试

### 错误 5：不记录改动

**问题：** 不知道究竟是什么改进了结果，或让结果变差
**解决方案：** 记录每次实验之间的改动内容

## 你的第一周行动计划

### 第 1 天：理解概念

- 完整读完这份指南
- 理解 runs、traces 和 projects
- 先别写代码，只理解概念

### 第 2 天：观察

- 给应用添加基础可观测性
- 运行几次
- 查看 traces

### 第 3 天：第一个数据集

- 手动创建 5 个简单测试样例
- 记录输入和期望输出

### 第 4 天：第一个评估器

- 写一个简单评估器（比如检查输出是否为空）
- 在一个样例上手动测试

### 第 5 天：第一次实验

- 让应用跑这 5 个样例
- 使用你的简单评估器
- 计算平均分

### 第 6 天：分析

- 看哪些样例失败了
- 理解原因
- 写下观察到的模式

### 第 7 天：第一次改进

- 做一个小改动来提升结果
- 再跑一次实验
- 比较分数

## 总结

评估和可观测性一开始可能看起来很复杂，但请记住：

1. **从简单开始**：先掌握基础概念和工具
2. **经常练习**：频繁进行小规模实验
3. **从失败中学习**：失败的测试最有价值
4. **逐步扩展**：只有在需要时才增加复杂度
5. **保持好奇心**：持续追问“为什么会这样？”

目标不是第一天就做到完美，而是通过系统化的观察和测试持续改进。



# 基础 案例

通过简单、可动手实践的 Python 脚本学习 agent 评估的**核心概念**。这是一个**以学习为核心的项目**，使用 Gemini 和 Langfuse 展示基本评估技术。

> **重要提示**：这是一个**学习项目**，不是生产系统。这里的示例做了简化，目的是更清晰地讲解概念。

## 这个项目真正会教你什么

**核心概念**（你将学到）：

- **基础 Tracing**：如何看到 agent 在做什么
- **工具监控**：跟踪函数调用和执行结果
- **添加元数据**：为 traces 增加上下文
- **创建评分**：把评分附加到 traces 上
- **简单评估**：基础版的 LLM-as-a-Judge 实现

**这个项目不会覆盖什么**（生产级内容）：

- **真实成本跟踪**：真实 token 使用量与价格
- **性能分析**：延迟拆解与性能优化
- **生产环境调试**：真实问题定位与修复
- **全面测试**：大规模评估数据集
- **真实用户反馈**：真实的用户反馈界面

## 前置条件

- **Python 3.12+**
- **Gemini API key** - 可在 [aistudio.google.com/apikey](https://aistudio.google.com/apikey) 免费获取
- **Langfuse 账号** - 可在 [cloud.langfuse.com](https://cloud.langfuse.com) 免费注册

## 快速开始

### 1. 安装依赖

```bash
uv sync
```

### 2. 配置你的密钥

```bash
cp .env_backup .env
```

然后把 `.env` 中的内容替换为你自己的 key：

```env
GEMINI_API_KEY=your-gemini-key-here
LANGFUSE_PUBLIC_KEY=pk-lf-your-key-here
LANGFUSE_SECRET_KEY=sk-lf-your-key-here
```

## 会跟踪什么（基础层级）

每个 trace 会记录：

- **LLM 调用**：使用了哪个模型、基本耗时
- **工具执行**：输入、输出、基础耗时
- **自定义元数据**：`user_id`、`session_id`、`tags`
- **评分**：附加到 trace 上的基础分数

**注意：** 这里只是基础跟踪。生产系统通常还会包含更详细的成本分析、性能指标和全面监控。

# OpenInference 和 Langfuse 

**简单来说：**
- **OpenInference** = 插桩/埋点 (Instrumentation) - 负责在代码中自动采集数据
- **Langfuse** = 监控后台/观测平台 (Observability Platform) - 负责接收、存储和展示数据

**详细解释：**

| 组件 | 角色 | 作用 |
|------|------|------|
| **OpenInference** | 插桩层 | 自动捕获 Agent 的运行数据 |
| **Langfuse** | 监控后台 | 接收、存储、展示追踪数据 |

**数据流向：**

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  OpenAI Agents  │────→│  OpenInference   │────→│    Langfuse     │
│    SDK 代码      │     │  (自动插桩采集)   │     │  (监控后台展示)  │
│                 │     │  - 捕获输入输出   │     │  - 存储数据     │
│                 │     │  - 记录时间戳     │     │  - 可视化界面   │
│                 │     │  - 提取元数据     │     │  - 分析统计     │
└─────────────────┘     └──────────────────┘     └─────────────────┘
```

**OpenInference 的职责：**
- 自动拦截 Agent 的调用
- 捕获输入 prompt、输出结果
- 记录 token 使用量、执行时间
- 提取工具调用、handoff 等信息
- 将数据转换为标准格式（OpenTelemetry）

**Langfuse 的职责：**
- 接收来自 OpenInference 的数据
- 持久化存储追踪记录
- 提供 Web 界面查看执行流程
- 支持数据分析、成本统计、调试

**类比理解：**
- OpenInference 就像**摄像头**（采集画面）
- Langfuse 就像**硬盘+显示器**（存储+展示）

**为什么需要两者配合？**

这种设计实现了**采集与存储的解耦**：
- 不换代码，只改配置就能切换监控平台
- 可以同时发送数据到多个平台
- 使用标准化的 OpenTelemetry 格式，生态兼容性好

OpenInference 可以把数据发送到多个后端：
- Langfuse
- Phoenix (Arize)
- Jaeger
- 其他 OTLP 兼容平台
