## 什么是 JSON-RPC 2.0？

JSON-RPC 2.0 是一种轻量级、无状态的远程过程调用（RPC）协议，它以简单、标准化的方式支持通知（notification）与远程方法调用。它使用 JSON（JavaScript Object Notation）作为数据格式，因此很容易与各种编程语言和平台协作。该协议与传输层无关，也就是说，它既可以跑在 HTTP 上，也可以跑在 WebSocket 上，甚至可以运行在任何其他消息传递环境中。

从本质上说，JSON-RPC 2.0 定义了一组数据结构，以及处理这些数据结构的规则。它以“简单”为设计目标，因此成为构建 API 和分布式系统时非常流行的选择。

### 关键概念

#### 1\. Request Object（请求对象）

一次远程过程调用，是通过向服务器发送一个 `Request` 对象来发起的。这个对象包含以下成员：

  * **`jsonrpc`**：一个字符串，用于指明 JSON-RPC 协议版本。在 2.0 版本中，这个值 **必须** 精确等于 `"2.0"`。
  * **`method`**：一个字符串，表示要在服务器上调用的方法名。
  * **`params`**：一个结构化值（可以是 `Array` 或 `Object`），用于承载方法参数。如果该方法不需要参数，这个成员可以省略。
  * **`id`**：由客户端设置的标识符。它可以是字符串、数字或 `null`。如果没有包含这个字段，那么该请求会被视为一个“通知（notification）”。

#### 2\. Notification（通知）

通知是一种特殊的 `Request` 对象，它不包含 `id` 成员。当客户端发送通知时，就意味着它并不关心服务器是否返回响应。服务器 **不得** 对通知做出回复。

通知非常适合一类单向通信场景，例如发送事件或记录日志。不过，由于它没有对应响应，客户端也就无法感知执行过程中是否发生了错误。

#### 3\. 参数结构（Parameter Structures）

调用带参数的方法时，`params` 可以有两种组织方式：

  * **按位置（By-position）**：`params` 是一个 `Array`，其中每个值按照服务器期望的顺序依次对应参数。
  * **按名称（By-name）**：`params` 是一个 `Object`，其中每个键值对都表示一个具名参数。

#### 4\. Response Object（响应对象）

当客户端发起的是标准 RPC 调用（而不是通知）时，服务器 **必须** 返回一个 `Response` 对象。它包含以下成员：

  * **`jsonrpc`**：JSON-RPC 协议版本，**必须** 为 `"2.0"`。
  * **`result`**：该成员在调用成功时 **必须存在**。其值由服务器上被调用的方法决定。如果发生错误，则 **不得** 出现该字段。
  * **`error`**：该成员在发生错误时 **必须存在**。如果没有错误，则 **不得** 出现该字段。其值是一个 `Error` 对象。
  * **`id`**：该成员 **必须存在**，并且 **必须** 与请求对象中的 `id` 保持一致。

一个 `Response` 对象 **只能包含 `result` 或 `error` 其中之一**，不能同时出现。

#### 5\. Error Object（错误对象）

如果 RPC 调用过程中出错，那么 `Response` 对象中的 `error` 字段会包含如下结构：

  * **`code`**：整数，表示错误类型。
  * **`message`**：对错误的简短单句描述。
  * **`data`**：一个原始值或结构化值，用于承载更多错误细节。这个字段是可选的，其格式由服务器定义。

下面是一些预定义错误码：

| Code | Message | Meaning |
| :--- | :--- | :--- |
| -32700 | Parse error | 服务器收到了无效 JSON |
| -32600 | Invalid Request | 发送的 JSON 不是合法的 Request 对象 |
| -32601 | Method not found | 方法不存在或不可用 |
| -32602 | Invalid params | 方法参数无效 |
| -32603 | Internal error | JSON-RPC 内部错误 |
| -32000 to -32099 | Server error | 保留给实现自定义的服务器错误 |

#### 6\. Batch Requests（批量请求）

如果客户端想一次发送多个 `Request` 对象，可以发送一个由多个 `Request` 对象组成的 `Array`。服务器会处理这些请求，并返回一个包含相应 `Response` 对象的数组。服务器可以按任意顺序处理批量请求，响应返回的顺序也不一定与请求顺序一致。客户端应通过每个请求的 `id` 来匹配对应响应。

### 示例

下面是一些 JSON-RPC 2.0 的实际示例：

**带位置参数的 RPC 调用：**

*客户端发送：*

```json
{"jsonrpc": "2.0", "method": "subtract", "params": [42, 23], "id": 1}
```

*服务器响应：*

```json
{"jsonrpc": "2.0", "result": 19, "id": 1}
```

**带名称参数的 RPC 调用：**

*客户端发送：*

```json
{"jsonrpc": "2.0", "method": "subtract", "params": {"subtrahend": 23, "minuend": 42}, "id": 3}
```

*服务器响应：*

```json
{"jsonrpc": "2.0", "result": 19, "id": 3}
```

**一个通知（notification）：**

*客户端发送：*

```json
{"jsonrpc": "2.0", "method": "update", "params": [1, 2, 3, 4, 5]}
```

*(服务器不会返回任何响应)*

**调用一个不存在的方法：**

*客户端发送：*

```json
{"jsonrpc": "2.0", "method": "foobar", "id": "1"}
```

*服务器响应：*

```json
{"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": "1"}
```

### 扩展（Extensions）

所有以 `rpc.` 开头的方法名都保留给系统扩展使用，不应用于其他用途。

## **为什么 Model Context Protocol（MCP）选择 JSON-RPC，而不是 REST？**

**Model Context Protocol（MCP）** 之所以选择 **JSON-RPC** 而不是 REST，背后有一系列技术与战略层面的原因。理解这一点，也会帮助你在设计或集成 agent 框架时拥有更强的判断力。

---

### **1. Agent / 模型操作需要的不只是 REST 的 CRUD**

REST 是围绕 CRUD（Create、Read、Update、Delete）设计的，它把 HTTP 动词（`GET`、`POST`、`PUT`、`DELETE`）映射到资源操作上。但像 MCP 这样的 LLM / Agent 编排协议需要的是另一种能力：

* **过程式 / 命令式交互（Procedural / Command-like Interactions）：**  
  MCP 会涉及一系列更丰富的操作，例如：开始、取消、恢复、流式输出、调用工具、管理提示状态等，这些行为并不能自然地映射到 CRUD 模式中。

**JSON-RPC** 天生就是为了 *远程过程调用* 而设计的，也就是“像调用本地函数一样，调用另一台计算机上的函数”。换句话说，它更适合表达：“请帮我执行这件具体的事，并把结果返回给我。”

---

### **2. 更适合多路复用与流式支持**

* **同一连接上执行多个调用：**  
  JSON-RPC 很适合那些需要保持一个长连接（例如 WebSocket、HTTP/2、SSE），并在其中实时发送多个命令与响应的协议。相比之下，REST（尤其是在 HTTP/1.1 场景中）通常是一条请求对应一次动作。

* **流式输出与通知：**  
  在 Agent 场景下，你可能希望拿到进度更新、部分结果，或者服务端主动发出的消息（notifications）。  
  JSON-RPC 原生支持 *notification*（单向消息），这在 REST 里并不是标准或自然的用法。

---

### **3. 显式方法名与结构化请求**

* **在 REST 中，操作由 URL + HTTP 动词共同定义。**  
  但在 JSON-RPC 中，你会直接看到这样的结构：`{"method": "tools/call", ...}`，也就是说动作本身是显式可见的，不是隐藏在 URL 和 HTTP 动词组合中的。

* **更容易扩展：**  
  如果要增加新能力，只需要增加新方法，不需要重新发明新的 URL，也不需要过度扩展 HTTP 语义。

---

### **4. 无状态协议 vs 有状态工作流**

* **MCP 可以运行有状态工作流**（例如会话、恢复、工具资源管理等），因此更适合使用一种既能表达状态变化、又能表达直接过程调用的协议。
* REST 更适合无状态、面向资源的操作。

  ##### 如果 JSON-RPC 是无状态的，MCP 为什么还能做有状态工作流？
  * “状态”其实是由服务器（或 agent）维护的，而不是由协议本身维护。

  * MCP 会使用诸如 `session_id`、`context_id` 或其他 token / ID，帮助服务器追踪当前进行中的工作流或对话。

  * 每次 JSON-RPC 调用都会附带必要信息（如 session / context），让服务器知道当前请求属于哪一个工作流或对话。

---

### **5. 更强的错误处理能力**

* **JSON-RPC 为每个请求定义了标准化、结构化的错误响应格式**，即 `error` 对象，其中包含 code、message 和 data。
* REST 的错误处理则没那么统一，往往是状态码 + 任意格式的负载，风格差异很大。

---

### **6. 与 IDE 协议生态天然对齐**

* **LLM agent 与工具系统，在设计上深受语言服务器、调试器、IDE 插件等协议影响，而这些协议中有很多都使用 JSON-RPC。**
* 例如：LSP（Language Server Protocol）和 Debug Adapter Protocol，都是基于 JSON-RPC 的。

---

### **总结表**

| Feature        | REST                     | JSON-RPC（MCP 使用） |
| -------------- | ------------------------ | ----------------------------- |
| 范式 | 面向资源 / CRUD | 远程过程调用（RPC） |
| 操作方式 | 限于 HTTP 动词 | 任意具名方法 |
| 流式支持 | 较复杂，缺少统一标准 | 原生适配 WebSocket / SSE |
| 多路复用 | 每次操作通常一个 HTTP 请求 | 单连接中可承载多次调用 |
| 通知机制 | 不够自然 | 内建支持 |
| 错误处理 | 风格不统一 | 结构化，协议内定义 |
| 状态性 | 最佳实践偏无状态 | 可以支持会话 / 状态工作流 |
| 可扩展性 | 需要变更 URL / 方法设计 | 直接新增方法即可 |

---

### **面向未来的理解：**

像 MCP 这样的协议，不是为了传统 CRUD API 设计的，而是为了 **AI 编排的未来** 设计的。它们需要：

* 对模型上下文和工具进行细粒度控制，
* 支持实时交互和通知，
* 具备一致性与可扩展性。

**JSON-RPC 天然就是为这些需求而生的**，因此相比 REST，它更适合高级 agent / 模型协议。  
如果你正在规划 LLM 系统，或者准备在大规模场景中集成 AI Agent，那么理解并善用这些协议设计选择，会让你明显走在前面。
