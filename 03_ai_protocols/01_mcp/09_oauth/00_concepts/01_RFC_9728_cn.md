# 什么是 RFC 9278：“Protected Resource Metadata Discovery”？

RFC 9278“Protected Resource Metadata Discovery（受保护资源元数据发现）”定义了一种简单方法，让客户端应用能够弄清楚**如何获取授权**，从而访问一个受保护资源，例如某个 API。

简而言之，它规定了一种机制：让 API（也就是“Resource Server”）告诉客户端应用，**去哪里找到它的说明书** 也就是“Authorization Server”（AS）及其相关元数据。

### 它解决了什么问题

假设一个客户端应用想访问 `https://api.example.com/data` 上的数据。为了做到这一点，它需要一个 access token。但客户端并不知道：

  * 哪个 Authorization Server（AS）会为这个 API 签发 token？
  * 需要什么类型的 token？
  * 访问 `/data` 需要哪些 scope 或权限？

客户端需要一种标准化方式来“发现”这些信息，而不是把它们硬编码在程序里。

-----

### 解决方案：`as_uri`

RFC 9278 提供了一个简单方案。当客户端对受保护资源（`https://api.example.com/data`）发起未认证请求时，Resource Server（也就是 API）可以拒绝请求，并返回 `401 Unauthorized` 状态码。

关键在于，服务器还会在 `WWW-Authenticate` HTTP Header 中带上 **`as_uri`**（Authorization Server URI）参数。

下面是一个可能的响应示例：

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer as_uri="https://auth.example.com"
```

这个 `as_uri` 明确告诉客户端：去 `https://auth.example.com` 找到 authorization server 的 metadata。

-----

### 如何发现 Metadata

一旦客户端拿到了 `as_uri`，它就可以向该 URL 发起标准请求，以获取 AS 的 metadata。这个 metadata 文档通常遵循 [RFC 8414](https://www.rfc-editor.org/info/rfc8414)（“OAuth 2.0 Authorization Server Metadata”）定义的格式，里面包含客户端继续完成授权所需的全部信息，例如：

  * **`issuer`**：Authorization Server 的标识符
  * **`authorization_endpoint`**：引导用户登录的 URL
  * **`token_endpoint`**：客户端用来把 authorization code 换成 access token 的 URL
  * **`scopes_supported`**：AS 能授予的全部权限列表
  * **`response_types_supported`**：支持的授权流类型（例如 `code`、`token`）

通过这种发现机制，客户端应用就可以动态配置自身，使其能够与任何支持这一标准的 API 对接，从而让系统更灵活，也更解耦。
