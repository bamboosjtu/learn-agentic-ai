# AI Agents 与 Workflows：技术对比

## 引言

在 **agentic AI 系统**领域，开发者在构建大语言模型（LLM）应用时，通常可以在两类宽泛的架构路径之间做选择：**工作流驱动系统**与**自主智能体系统**。这两种方式都可能会让 LLM 使用工具和外部数据，但它们在流程如何组织、如何控制上存在根本差异。本文基于 Anthropic 的 *Building Effective Agents* 指南，对 AI agents 与 workflows 做一份技术层面的比较。我们会先定义这两种范式，再从几个关键维度展开对照，包括：**目的与设计意图、架构与执行模式、灵活性与自主性、适用场景、开发复杂度**，以及 **可观测性与控制**，帮助 agentic AI 开发者为自己的需求选择合适的方法。

## 定义

### AI Workflows

&#x20;*提示链式 **workflow** 模式示例：将任务拆解为顺序执行的多次 LLM 调用，并在中间加入 **“闸门”** 检查，以确认流程达到预期后再继续。*

**AI workflows** 指的是：通过**预定义代码路径**和一系列固定步骤来编排一次或多次 LLM 调用的系统。在 workflow 中，开发者会显式定义子任务或分支决策的顺序，例如先生成提纲，再校验提纲，再扩写内容；LLM 则在每一步接收特定提示词完成相应任务。这会产生一种**规定式、确定性流程**：整体任务如何完成，其逻辑是由开发者硬编码好的。

Workflow 强调 **可预测性与一致性**：对于相同输入，它每次都会遵循同一套脚本化流程。Workflow 中的 LLM 往往会结合工具调用或检索能力进行增强，但它并不会决定“下一步该做什么”，这是由外围代码编排的。正因为路径是固定的，workflow 特别适合那些可以事先被**清晰拆解**或分类的问题。

### AI Agents

&#x20;*一个 **自主 agent** 循环示意图：agent 迭代地规划动作、调用工具或外部 API、观察结果，并调整计划，直到任务完成（或触发停止条件）。*

相比之下，**AI agents** 是一种**基于 LLM 的自主系统**，由 LLM 自己**动态控制其行动序列以及工具使用方式**。一个 agent 通常先从人类那里接收一个高层目标或命令，然后在没有固定脚本的情况下，内部**规划策略**并进入循环执行。

在每一步里，agent 都会基于当前上下文和鼓励规划的提示词，自己决定下一步做什么，比如是否调用某个工具、检索信息、提出澄清问题，或者直接给出最终回答。关键在于：agent 会利用**环境反馈**（例如工具调用结果、代码执行输出等）来指导下一步动作。这个反馈循环会一直持续，直到 agent 判断目标已经达成，或命中预定义停止条件。

简而言之，agent 提供的是**灵活性与模型驱动决策**：LLM 可以自由处理意外情况，或者临场调整计划，而不是严格沿着预编码路径前进。

## 关键差异总览

下表总结了 workflow 系统与自主 agent 在若干维度上的关键差异：

| **维度** | **LLM Workflows**（预定义编排） | **Autonomous AI Agents**（动态规划器） |
| --- | --- | --- |
| **目的与设计意图** | 面向**可预测性**与一致性，适合定义清晰的任务。开发者预先确定步骤或分支，以确保输出稳定可靠。常用于无需完全自主性的场景。 | 面向**灵活性**，适合开放式或复杂任务。通过让 LLM 自主决策与动态适应，处理无法完全预定义步骤顺序的场景。强调模型的自主性与主动性。 |
| **架构与执行** | 由代码编排的 **静态序列或静态流程**，包括 LLM 调用和工具调用。遵循开发者定义好的固定 **workflow graph** 或脚本，例如提示链、路由逻辑、并行子任务。错误检查与分支由显式代码实现，例如闸门校验。 | 通过 **动态循环** 执行，LLM 会**迭代地规划并执行动作**。Agent 维护内部计划，根据环境选择工具或下一步行为。通常实现为一个在循环中调用工具并利用结果反馈的 LLM。整体架构往往很轻，只包含循环与工具集，控制流主要依赖 LLM。 |
| **灵活性与自主性** | **自主性有限**。LLM 只能在预定义步骤范围内运行。灵活性较低：如果输入不符合预期流程，workflow 很难自我调整，除非开发者已显式在代码中预留这种变化。优点是行为更可预测，缺点是对新情境适应能力较弱。 | **自主性高**。LLM **可自行控制行动，并对步骤顺序做即兴调整**。Agent 能处理意外输入，或主动增加开发者未预设的步骤。这种灵活性也伴随**更高的错误风险或非预期行为风险**，尤其当 agent 推理失误时。开发者必须对模型决策有较高信任。 |
| **主要应用场景** | 适合**结构良好、可预先拆解**的问题。例如：多步内容生成（提纲 -> 草稿 -> 修订）、数据处理流水线、固定步骤的表单填写或数据库查询、按类别把输入路由到不同提示词或模型。通常用于问题边界已知、且正确性与一致性最重要的场景。 | 适合**开放式、复杂任务**，尤其是那些*“很难或几乎不可能预测所需步骤数量”*的问题。例如：跨多个文件自主编写和调试代码的 agent；需要在对话中检索并综合信息的研究助理；既要处理自由对话又要采取行动的客服机器人。当**动态决策**与适应性很重要时，agent 更有优势。 |
| **开发复杂度** | 对于已知任务，通常**更容易实现和调试**。很多 workflow 模式（如 prompt chaining）只需几行 API 调用即可实现。由于逻辑显式可见，错误更容易定位和复现。但分支很多时，workflow 也会变得难维护，改动需要更新代码。过度依赖厚重的 agent 框架还会引入不必要复杂度，因此理解简单模式很有价值。 | Agent 的核心循环代码本身可能**很直接**，但要把它做得稳健，**整体复杂度更高**。你需要投入更多提示词工程工作，也必须做大量测试，才能信任它在多样场景中的表现。工具和接口也必须被精心设计与文档化，因为它们是 agent 用来行动的“控制旋钮”。在实践中，构建一个优秀 agent 往往需要大量 prompt 调优与工具优化。Anthropic 就提到，他们在构建代码 agent 时，花在工具定义优化上的时间比花在 prompt 上的更多。 |
| **可观测性与控制** | **可观测性高**。每一步都由开发者掌控且已知。你可以记录中间输出，并在特定点施加检查或约束，例如用校验闸门捕捉错误或跑偏结果。一旦出错，workflow 通常会停止，或进入已知的错误处理分支。开发者对何时调用模型、调用哪个工具、如何处理异常拥有细粒度控制。 | **天然可观测性较低**，因为 agent 自己决定路径。若没有额外设计，外部很难看清它“在想什么”或为什么采取某一步。最佳实践是**提升透明度**，让 agent **显式叙述或记录其计划与步骤**。控制也更间接：开发者设定的是高层策略，例如迭代上限、工具使用限制和护栏，而执行过程中 agent 在自行选择。为了维持监督，常见手段包括：在关键节点暂停等待人工批准、在每一步使用**环境反馈**、定义清晰停止条件（最大迭代次数等）。同时建议用严格的沙箱测试与护栏来防止和缓解错误。 |

## 目的与设计意图

在 workflow 与 agent 之间做选择时，系统的**预期目标**是首要考虑因素。

Workflow 型系统是为**定义清晰的问题**而设计的，在这类问题中，解决过程大体已经可以提前理解。开发者的意图是**把解决路径显式编码下来**，从而确保输出稳定一致。Anthropic 指出，对于这类边界明确的任务，workflow 在**可预测性与一致性**上更有优势。

换句话说，如果你已经知道一个任务应该按什么步骤完成，那么你就可以把这些步骤编程出来，让 LLM 在每一步中填充具体内容。这通常能带来更高可靠性，因为 LLM 被置于一个结构化流程中，例如始终先总结再分析，或始终通过二次检查来验证答案。代价是：workflow 的灵活性只存在于开发者事先想到的范围内。它的目的不是创造性探索，也不是处理全新的需求；它的强项在于**重复已知流程**，并在每一步利用 LLM 的理解与生成能力。

而 AI agent 的设计意图，则是解决那些**开放式或复杂**、且*无法被事先整齐映射为固定流程*的问题。Agent 的目标是成为**自适应的问题求解器**。开发者会给 agent 配置工具、初始提示词（例如引导其推理与行动的指令）以及一些宽泛约束，但**不会把精确步骤硬编码进去**。这种设计使 agent 能处理步骤数量和类型都难以预测的任务。

例如，一个 agent 可能决定通过多轮查询研究某个主题、整合信息、必要时向用户请求澄清、然后写出报告，而开发者并没有显式列出这些子任务。这里的核心目的是借助 **LLM 自身的推理与规划能力**来寻找解决路径。正如 Anthropic 所说，当*“在大规模场景下需要灵活性和模型驱动决策时”*，agent 更合适。

总结来说，**workflow** 采用的是一种*“先有解法，再实现步骤”*的思维方式；而 **agent** 采用的是一种*“先有目标，再让 AI 自主找路径”*的思维方式。

需要强调的是，更高自主性并不总是更好。Anthropic 的指南强调，应当从**最简单可行的方案**开始，只有在必要时才逐步提升到 workflow 或 agent。如果一个单提示词、或一个非常简单的链式调用就能完成任务，那么这种简单性往往比更重的 agentic 系统表现更好。Agent 增加的自主性往往伴随更复杂的行为，也会引入新的失败模式。因此，设计意图必须与问题需求对齐：对于**直接、明确的任务**，优先用 **workflow**；对于需要主动性与适应能力的任务，再考虑 **agent**。

## 架构与执行模式

Workflow 与 agent 的架构差异，核心在于控制流如何组织。

* **Workflow 架构：** Workflow 本质上是一个由传统代码编排的 *LLM 调用与工具调用的有向图或顺序序列*。开发者显式规定调用顺序：上一步输出可能作为下一步输入。Workflow 常见的**执行模式**包括：

  * *Prompt chaining*：把任务拆成一串线性子任务，中间可插入检查。
  * *Routing*：先做分类，再把输入路由到不同的专用提示词或模型。
  * *Parallelization*：把任务拆成若干独立部分并行处理，例如多个 LLM 分别处理不同片段，或者多次尝试同一任务后投票。
  * *Orchestrator-worker*：中心协调者 LLM 拆解子任务给多个 worker LLM，再汇总结果。
  * *Evaluator-optimizer loops*：一个 LLM 先生成方案，另一个负责评估并反馈，必要时循环优化。

  在这些模式里，*执行路径都是预先确定好的*。例如迭代次数、分支结构由代码设定，而不是由 LLM 临场决定。即便 orchestrator LLM 会动态生成子任务内容，“有一个 orchestrator 步骤”这件事本身依然是架构设计里固定存在的。每一步通常都有明确角色和提示词。

  更重要的是，开发者可以在 workflow 中插入错误处理逻辑和校验步骤。比如某一步结束后，代码可以检查 LLM 输出是否满足某些标准（也就是 prompt chaining 中的“闸门”），如果不满足，就继续、重试，或者直接退出。这种显式控制流让整个架构**高度透明**，你可以把它画成流程图，而且每条路径都是已知的。

* **Agent 架构：** Agent 的架构则更加**流动**。通常，一个 agent 被实现为一个循环，在每次迭代中：

  1. Agent（LLM）观察当前状态，其中包括用户请求、之前步骤的中间结果、历史记忆等。
  2. Agent **决定下一步动作**，例如调用工具（搜索、计算器、代码执行器等）、输出最终答案、提出澄清问题等。
  3. 如果采取了动作（如工具调用），环境会返回结果，这些结果再被写回 agent 上下文，供下一步使用。
  4. 循环持续，直到 agent 宣告完成，或触发停止条件。

  这一架构最关键的点在于：动作序列**不是由代码预先写死的**，而是*由 LLM 的逻辑决定*。Anthropic 将 agent 概括为“**在循环中基于环境反馈使用工具的 LLM**”。这意味着，从代码层面看，一个 agent 可能很简单，例如一个 `while` 循环，不断把对话状态和工具输出喂给 LLM；但其*涌现行为*可能非常复杂。

  Agent 的提示词（也叫 policy 或 system prompt）非常关键，它必须指示 LLM 如何逐步规划、推理和使用工具。常见架构做法是让 LLM 以某种结构化格式输出计划，或输出工具调用命令，再由 agent 循环去解释并执行。通常还要区分 agent 的**规划输出**与**行动输出**。例如，agent 可能会先在内部形成“我应该搜索 X”的想法，再输出一个结构化调用指令去真正执行搜索工具。架构需要能捕捉这类输出、执行工具，并把结果追加回上下文。

  从**架构策略**角度看，agent 内部还可能采用多种模式：

  * **工具增强推理：** Agent 从一组工具中选择搜索、计算器、代码运行器等来获取信息或执行动作。工具接口设计是架构的一部分，每个工具都要给 agent 提供清晰指令和输入输出 schema。
  * **自我拆解：** 与开发者预设的 prompt chain 不同，agent 可以在运行时把问题拆成子问题。这有点像 orchestrator-worker，但 orchestrator 不是一个硬编码模块，而是 agent 自己决定“现在应该拆成哪些子任务”。例如面对复杂请求时，agent 可能动态决定“把它拆成 3 个问题分别处理”。
  * **迭代式优化：** Agent 自己可以包含内部评估循环，例如先生成草稿，再自我批判并改进。如果觉得有必要，它会主动这样做。不同于固定的 evaluator-optimizer workflow，这里是 agent **自行决定**是否进入该循环。

  由于 agent 的执行模式是动态的，其架构还必须包含**安全与错误处理机制**，而这些机制不再只是“跳到某个固定错误分支”。Agent 被期望在推理过程中自己处理错误。例如，若某个工具调用失败或返回无用结果，一个设计良好的 prompt 可以引导 LLM 换一种方法，或向用户请求帮助。Anthropic 也指出，如今更先进的模型已经具备在自主运行中**从错误中恢复**的能力，而这是构建可靠 agent 的关键。开发者通常还会加入**迭代次数上限**，或者其他 fail-safe，例如防止重复无意义动作，以避免死循环或退化行为。

总结来说，workflow 的架构更像是**固定编排的管道**，而 agent 的架构更像是一个**由 AI 决定下一事件的事件循环**。Workflow 借助清晰的结构化模式进行组合和嵌套；agent 则依赖 LLM 在简单循环框架内涌现出的规划能力。实际选择往往取决于：你能否把任务封装成一个已知顺序。如果可以，优先 workflow；如果需要一个开放循环，让 AI 自己决定顺序，那就需要 agent。

## 灵活性与自主性

Workflow 与 agent 最鲜明的对比，也许就体现在它们的**自主性**和执行灵活性上。

一个 **workflow 系统的自主性有限**：LLM 只能沿着代码为它规定好的路径前进。假设一个 workflow 包含三个步骤（分析 -> 转换 -> 验证），那么 LLM 就会按这个顺序被调用三次，*无法偏离*。唯一的灵活性来自开发者显式编写的分支，例如一个 `if/else`，根据分类结果走向不同子流程。但即便如此，这个分支点本身仍是预定义的。

本质上，workflow 处理变化的方式是**枚举法**：开发者提前设想任务可能出现的变化，并为每种情况写好处理逻辑。超出这些设想范围的输入，通常会让 workflow 失败，或产生次优结果。这让 workflow 十分**可控**：它不会做出激进的意外行为，因为它*根本做不到*。但反过来，一旦输入需要一种全新的处理方式，它也容易变得脆弱。

而 **agent 拥有更高的自主性**：它能够通过临场决策，处理那些未被显式编程覆盖的情况。给定一个宽泛目标，agent 可以在其工具集和知识边界内自行寻找达成路径。Anthropic 认为，agent 适合解决那些*“很难或不可能预测所需步骤数，且无法硬编码固定路径”的问题*。因为 agent 决定走多少步、做哪些动作，所以它可以根据需要灵活扩展或调整计划。

例如，一个研究型 agent 第一次搜索后发现信息量太大，它可以决定先做摘要，再做一次更聚焦的搜索。而刚性 workflow 若没有预先为这种情况设计路径，通常无法做到这一点。正是这种自主性让 agent 很强大，但同时也引入了**不确定性**。Agent 可能走一条开发者没有预想到的路径，这条路径可能很巧妙，也可能完全错误。

**自主性的高低**也决定了错误和新情况如何被处理。由于缺乏自主性，workflow 在遇到未预见场景时，通常只能失败、停止，或者进入某个简单 fallback。Agent 则可能识别到结果异常，并尝试自我恢复，例如发现某个工具返回结果不合理后，改用另一个工具，或换一种查询方式。现代 LLM agent 已经展现出**从错误或死路中恢复**的能力，会通过修正计划来继续前进。

但与此同时，自主性也容易导致**错误叠加**。如果 agent 在早期做出错误决策，它可能会在错误状态之上继续推演和执行更多动作。Anthropic 也提醒，自主 agent 更容易出现这种累积性错误，因此必须配合护栏、迭代限制等手段使用。

在实践中，选择更高自主性（即 agent），本质上就是**用部分控制权换取灵活性**。如果问题域定义明确，且错误代价不可接受，那么高自主性往往并不必要，甚至是风险；这时 workflow 已经足够，而且更容易建立信任。但如果问题域本身复杂，存在大量边缘情况甚至未知未知，例如一个需要在真实计算机环境中解决任意用户请求的 agent，那么自主性就变得必要。此时开发者就必须通过严格测试和**信任校准**来控制风险，例如先在受限或沙箱环境中运行 agent，待它证明自己足够可靠后，再逐渐扩大自治范围。

## 使用场景

**Workflow 的适用场景：** Workflow 最适合**结构化、可重复的流程**。以下是一些典型例子，以及 workflow 为什么适合它们：

* *内容生成流水线：* 如果你需要分阶段生成文本，例如先让 LLM 产出提纲，再按标准校验提纲，最后扩写为完整文章，那么 workflow 就很自然。每个阶段都是明确子任务。Anthropic 也举过类似例子，比如先写营销文案，再翻译文案；或者先列文档提纲，再完成写作。这种情况下，步骤顺序（写 -> 检查 -> 重写）是已知的，完全可以编码为 prompt chain。
* *数据或查询路由：* 假设一个 AI 系统处理客户请求，有些请求要查数据库，有些请求适合触发预设回复等。那么 workflow 可以先做路由分类，再调用对应后续步骤。另一个例子是根据输入复杂度，决定把问题送给不同模型或不同提示词。Anthropic 就提到：简单问题交给更小更快的模型，复杂问题交给更大模型以提升准确率。
* *并行分析：* Workflow 非常适合利用并行性。例如，对文档不同部分同时做分析，再把结果汇总；或者让多个 LLM 同时尝试同一个任务，再通过“投票”选择最佳结果，提高可靠性。只要任务可以被拆开，并行 workflow 就很有价值。
* *确定性的工具调用：* 如果必须以稳定、可审计的方式使用工具（API、数据库、计算器），workflow 能让开发者精确控制何时、如何调用每一个工具。例如，一个 workflow 可以规定永远先从用户输入中提取固定字段，再用这些字段调用某个 API。LLM 只负责解释或转换结果，而不是决定“该调哪个 API”。

概括来说，workflow 的优势在于：**每一步都已知，而 LLM 的价值在于更聪明地执行这些已知步骤**。这类模式在企业场景中很常见，比如表单填写助手、固定格式报告生成、内容审核流水线等，因为这些场景最看重一致性与审计能力。很多 2023 到 2024 年早期 LLM 应用，就是以这类结构为主，因为它们更容易被信任，也更容易评估。

**Agent 的适用场景：** Agent 在**复杂、探索型任务**中更有优势，尤其是那些同时涉及推理、工具使用、交互的任务。典型场景包括：

* *代码助理 / 代码 agent：* 软件开发是自主 agent 最典型的落地领域之一。一个 agent 可以接收高层需求或 bug 描述，自主尝试写代码、修改代码来实现解决方案。Anthropic 提到过一种代码 agent：它能根据任务描述，在多个文件间读代码、改代码，并通过 benchmark 任务进行验证。这里，agent 可能需要理解现有代码、规划修改哪些文件和函数、应用编辑、运行测试、在测试失败后继续迭代。所需修改步骤和涉及文件数都无法预先确定，因此它天然适合 agent，而不是固定 workflow。代码问题还有一个好处：通常有清晰的真值反馈，例如测试是否通过，agent 可以用这个反馈来调整下一步。
* *“什么都能做”的通用助手：* 如果用户可以让 AI 做各种不同事情，例如答题、计算、联网查资料、操作文件等，那么一个带有工具集的自主 agent 更合适。举例来说，Anthropic 的“computer use”参考实现允许 Claude 像人一样操作电脑：打开浏览器、搜索信息、打开终端、运行命令等。对于这类开放范围任务，不可能提前枚举所有可能路径，必须由 agent 基于情境自行决策。
* *交互式客服 agent：* 正如 Anthropic 附录中提到的，客服是 agent 的很有前景的落地方向。客服 agent 需要处理开放式对话、检索用户数据或知识库内容、执行退款或预订等动作，还要在必要时向客户追问补充信息。对话流程随时可能变化，所以 agent 架构能更好地把自由对话与工具操作结合起来。此类任务的成功标准通常也很清晰，例如问题是否被解决，而 agent 可以被允许用多种策略尝试达成这个目标。
* *研究与分析助理：* 想象一个 AI agent 需要围绕某个主题撰写分析报告。它可能需要搜索资料、阅读并总结、形成草稿、向用户澄清目标等。这个过程本质上是一种研究 workflow，但它具体搜索到什么时候、跟进哪些信息源、如何组织写作结构，都不应是固定的，而应依赖运行时情况与用户高层目标。因此这天然更偏 agentic。
* *迭代型创意任务：* 对于长文写作、设计、排障等需要反复打磨的问题，agent 也很适合。例如，一个写故事的 agent 可以先写一段，再检查前后是否一致，调整人物与情节，然后继续写。这个过程不需要预设固定迭代次数。Workflow 虽然也能强行规定“写三轮”，但 agent 可以根据自己对当前质量的评估决定是否继续优化。

Agent 场景的共同特征是：需要**运行时的动态决策**，并且通常同时融合**对话与行动**。正如 Anthropic 所指出的，agent 在那些既要理解复杂输入（尤其是对话），又要在环境中采取动作的任务上，价值最大。它们尤其适合那些有明确成功标准、并且能获得反馈回路的场景，例如代码 agent 的测试反馈，或客服 agent 的用户回应。借助这些反馈，agent 能在运行过程中不断修正并提升效果，而静态 workflow 则很难做到这一点，除非相关逻辑早已被手写进去。

## 开发复杂度

构建 workflow 系统与构建 agent，会面对不同类型的复杂度。直觉上，人们往往认为自主 agent 更复杂，而在实践里通常也是如此，但其中仍有一些细微差别。

**Workflow 开发：** 构建 workflow 的核心，是要求开发者**分析任务并为其设计一套固定结构**。如果任务天然可以拆成几步，这件事很直接；但如果开发者试图为大量边缘情况都留好处理逻辑，结构也会快速变复杂。Workflow 中每增加一个分支或条件，代码复杂度就会增加。

但 workflow 的优势在于，一旦逻辑结构设计好，用 LLM API 调用和工具调用去实现它通常并不困难。Anthropic 甚至指出，很多多步模式只需少量 API 调用和简单胶水代码就能完成。你不一定需要复杂的编排框架，一个普通 Python 脚本往往就足以组织 prompt chaining、routing 等逻辑。这使得 workflow 的实现通常**简单而透明**。

Workflow 的调试也更容易理解，因为每一步都可以被单独测试，而且步骤转换是确定性的。如果某一步持续出错，你通常能明确知道该回头检查哪一段代码、哪一个 prompt。Workflow 开发的主要工作量集中在：**为每一步做 prompt engineering**，以及保证数据在步骤之间正确流动。

Workflow 开发也有一个常见陷阱：为了实现一个本质上静态的 workflow，反而过度引入通用 agent 框架或库，导致系统被不必要地复杂化。Anthropic 的工程文章提醒，市面上确实有很多框架可以简化 agentic 系统的开发，但这些框架往往会增加抽象层，**遮蔽底层 prompt，使调试更加困难**。它们还可能诱导开发者加入超出实际需求的复杂性。

因此，在实现 workflow 时，更推荐保持轻量：除非框架有明确收益，否则最好直接在你自己理解的代码中调用 LLM 和工具。理解系统“底层到底在做什么”很关键，因为对框架行为的错误假设，常常是出错的来源。总的来说，workflow 的复杂度更多是*前置在设计阶段*，即如何正确拆分任务；而在运行阶段，它的复杂度相对有限，因为执行路径已被约束住。

**Agent 开发：** 从表面上看，一个自主 agent 的外部实现可能很简单，例如一个不断把 prompt 和工具输出回灌给模型的循环。但真正的复杂度被**转移到了 prompt、工具设计，以及迭代中涌现出的行为**上。本质上，你不再主要通过显式代码来编排每一步，而是在通过模型的 prompt 与训练分布来“编程”。

这需要不同的思维方式，也需要大量实验。Agent 开发的关键挑战主要包括：

* **Prompt（策略）设计：** 你必须设计一个初始 prompt 或 system message，明确告诉 agent 应该如何行动，例如如何逐步思考、什么时候用什么工具、工具调用如何格式化、什么时候停止、糊涂时该怎么应对等。这通常需要大量试错。你可能需要在 prompt 中加入推理过程示例、工具使用示例等来引导模型。这个 prompt 编码的是 agent 的“策略”，设计正确并不简单。它不再只是“生成一个答案”的 prompt，而是要诱导 LLM 运行出一个*过程*。而这类过程型 prompt 的失败，往往很难直接定位，需要不断调整措辞或加入新样例。
* **工具接口设计：** 在 agent 中，工具是模型能力的延展，但前提是 agent 必须清楚地知道如何以及何时使用它们。Anthropic 非常强调工具集与工具文档的设计，因为 agent 的表现**极度依赖它是否真正理解这些工具**。每个工具通常都需要向 LLM 描述其名称、用途、输入格式和输出格式。如果这些描述不够清晰，或者工具使用过于复杂，agent 很容易误用。Anthropic 在附录中的工具工程建议包括：尽量让工具**更容易被正确调用**，例如选更简单的输入格式，避免强迫模型去产出难写的严格 JSON 字符串；在工具说明中加入示例；甚至通过重命名参数或拆分功能来减少混淆。在开发过程中，工具定义通常需要不断迭代：运行 agent，观察错误，再把接口改得对模型更友好。Anthropic 就举过一个例子：他们发现代码编辑工具使用相对路径时，agent 很容易在目录切换后混乱，于是改为始终要求绝对路径，结果工具使用马上稳定下来。这种围绕工具接口的调试，是 agent 开发特有的一类工作。
* **涌现式错误处理：** 与 workflow 由代码显式处理错误不同，agent 往往需要你去*引导模型自己学会处理错误*。例如，你可以在 prompt 中写：“如果上一个工具结果为空或没帮助，就尝试别的方法”，以帮助 agent 自我恢复。但模型仍然可能陷入死循环，或发出无效工具调用。此时开发工作就变成：分析 agent 的推理链，判断它为什么做出了坏决策。解决方法可能包括：在 prompt 中增加约束（例如“同一个查询不要重复超过两次”）、如果你在做强化学习则调整奖励机制，或者在外围代码中加一个简单规则用于打断无限循环。Agent 的调试天然带有更多不确定性，你必须覆盖多种场景测试，确认它足够稳健。Anthropic 也强烈建议，针对 agent 一定要做大量沙箱测试，因为它存在错误叠加和非预期行为的风险。
* **评估复杂度：** 对 workflow 而言，每个步骤都可以单独做单元测试，例如把固定输入喂给第 2 步，看结果是否符合预期。而对 agent，评估通常是整体性的：你需要跑完整场景，看看 agent 最终是否成功完成目标。Agent 往往需要你先定义成功标准（它是否正确完成用户请求），然后可能还要为此搭建模拟器或测试框架。这是一套比 workflow 更复杂的测试范式。但一旦评估框架建立起来，它也会反过来帮助你改进 agent，例如某些测试失败时，你就据此调 prompt 或补充示例。

从纯粹的**开发时间与精力**看，一个简单 agent 的原型也许比 workflow 更快搭起来，因为你只需要一个循环和一个 prompt，而不是手工设计多组 prompt 和步骤。但如果要让这个 agent **在多样案例中都足够可靠**，所需努力往往远远超过把一个 narrower 的 workflow 做稳。

Anthropic 的一个核心建议是：**只要可能，就保持 agent 设计简单。** 这可能意味着控制 agent 的任务范围，或者从更小的工具集开始，再逐步扩展。开发者很容易把 agent 设计得过于复杂，例如塞给它太多工具、太重的 prompt、太多职责，但这往往会适得其反。很多时候，一个简单、你充分理解并调优过的 agent，会比一个试图包打天下的复杂 agent 表现更好。

总之，**workflow** 的复杂度主要体现在*显式代码与分支逻辑*上，而 **agent** 的复杂度则更多体现在*隐式推理与 prompt 工程*上。对组织和开发者而言，workflow 更像传统软件工程前置设计的问题；而 agent 则要求一套新的、持续迭代的 prompt 调优与验证流程。Anthropic 的总体建议也与此一致：*“只有当更简单的方案不够时，才增加多步 agentic 系统。”* 换言之，如果不是真的需要那种灵活性，就不要过早承受 agent 的开发复杂度。

## 可观测性与控制

由于自主性不同，workflow 与 agent 在运行时的可观测性与可控性，以及如何监督和介入系统行为方面，也有显著差异。

对于 **workflow 系统**，可观测性通常很高，因为整个流水线是显式的。开发者可以在每一步插入日志，记录发给 LLM 的 prompt、LLM 的输出，以及编排代码做出的任何决策。由于每一步都是已知的，系统状态可以被非常细粒度地监控。

例如，如果存在路由步骤，系统可以记录每个输入走到了哪条路径；如果存在验证步骤，系统可以记录输出是通过还是失败。调试因此非常直接：通过查看日志，你通常可以精准定位是哪一步导致了失败，或哪一步产出了异常结果。

控制同样也很直接。开发者可以通过修改代码，轻松改变某一步的行为，或者加入新的条件。也就是说，开发者（或运维团队）围绕 LLM 保持着一个**紧密控制环**：外围代码“包裹”住每一次模型调用，以确保它按预期工作。

Workflow 还天然支持**程序化护栏**。比如，如果检测到某个中间 LLM 输出不合适或偏题，workflow 可以在继续之前将其丢弃或纠正。Anthropic 对 prompt chaining 的描述中就明确提到了加入一个*“闸门”*，也就是中间检查，用来验证流程是否还在轨道上。这个闸门可以很简单，例如检查提纲是否包含指定章节，或者在某一步用 moderation 模型过滤输出。

由于 workflow 的流程本来就是预定义的，加入这些检查不会破坏整体逻辑，反而是设计的一部分。此外，workflow 也更容易被设计成 fail-safe，例如检查失败时直接报错给用户，或回退到一个更简单的策略。其核心点在于：**对 LLM 的控制是外置于代码中的**。LLM 并不是一个真正自主行动的主体，而是一个输入输出都由外部程序管理的组件。

这种外部控制也让 workflow 在**合规与安全**层面更容易治理，例如你可以强制某些步骤必须发生，例如最终必须由人工审批，或输出前必须经过内容过滤。可观测性也延伸到了指标层面：因为每个阶段都是已知的，所以你可以统计“多少输入走了分支 A 或 B”“第 2 步重试了多少次”等数据，从而对系统行为形成清晰认知。

而对于 **自主 agent**，可观测性与控制都更难，因为整个过程是由 LLM 内部决策驱动的。默认情况下，如果你只是让 agent 自己运行，可能最后只看到它输出的最终答案，以及少量工具调用日志（前提是你有记录）。至于 agent 使用了什么推理过程，则在模型内部，除非你显式把它暴露出来。

因此，一个非常关键的最佳实践是：让 agent **显式暴露自己的思维链或每一步计划**，例如打印到日志中，或写进模型输出的某个专门部分。Anthropic 对 agent 的第二条核心原则就是：*“优先透明性，明确展示 agent 的规划步骤。”*

在实现上，这可能意味着：在 agent prompt 中要求模型输出自己的思考过程，虽然这些内容不一定展示给最终用户，但会被记录给开发者。有些 agent 框架还会提供所谓的“verbose mode”，让 agent 把自己的动作过程显示出来，例如“正在搜索 X -> 找到了 Y -> 下一步准备做 Z”。通过记录这些内容，开发者就能观察 agent 是如何做出决策的，这对于调试和审计极其重要。否则，agent 往往会像一个黑箱，让人无法解释它为什么会做出某个动作或给出某个答案。

Agent 的控制则更偏向间接式。常见方法之一是**设定约束**，例如限制 agent 可使用的工具范围、限制最大步骤数，防止跑飞。Anthropic 提到，可以通过*“停止条件（例如最大迭代次数）来维持控制。”* 另一种方法是把某些动作放在人类审批之后，例如 agent 可以起草一封邮件，但不能直接发送；或者在代码场景中，agent 可以提出代码修改，但必须由人类审查后才能真正执行。

Agent 还可以被设计成在不确定时主动求助于人类，例如 prompt 中鼓励 agent 在卡住时向用户请求指引。这些都是在一个原本自主运行的过程中植入控制的方法。

**人工监督**是 agent 可观测性 / 可控性的特殊形态。因为 agent 往往会运行很多步，一种常见策略是在中间关键节点暂停并请求反馈。例如，当 agent 制定完一个计划后，它可以先向用户展示：“这是我接下来打算做的事，要继续吗？” 这样用户或开发者就能在早期发现误解。另一个关键点可能是：agent 已经搜集完信息，正准备执行某个有后果的动作，例如运行代码、执行交易等，这时可以强制插入人工复核。

Workflow 当然也可以做人类在回路中的节点，但由于它本来就是显式流程，所以实现更直接：代码里插一个人工审批步骤即可。对于 agent，这件事更复杂一些：你必须让 prompt 或外围循环知道“什么时候该交出控制权”，或者周期性把控制权还给人类。但在高风险应用中，这种设计是必要的。

从**可靠性工程**的角度看，监控一个 agent 往往意味着记录它整个动作序列与结果。例如日志中可以写：在时间 t，agent 选择了工具 X，输入 Y，返回结果 Z。随着运行次数积累，这些日志可以帮助你识别共性失败模式。如果 agent 开始跑偏，要自动检测出来并不容易，可能还要引入另一个模型或启发式规则来判断 agent 是否混乱。某些团队会用第二个“watcher”模型去分析 agent 的思维过程。而在 workflow 中，这种跑偏检测往往已经通过每一步的预期输出或闸门机制内建完成了。

最后，针对 agent 的**护栏**往往更偏向“学习式”或“适应式”。Anthropic 建议通过沙箱环境和大量测试来逐步打磨这些护栏。例如，你可以在沙箱里故意喂给 agent 一些刁钻输入，看它会不会做出危险行为，再据此修改 prompt 或增加约束。你也可以配合自动评估或对抗性测试。相比之下，workflow 的护栏通常更静态，例如某个 `if` 条件判断。二者都需要护栏，只是 workflow 的护栏更多是代码的一部分，而 agent 的护栏经常是 prompt 与外部监控系统共同作用的结果。

总而言之，由于 workflow 的执行过程显式，确保系统的**可观测性**（你知道 AI 在做什么）和**可控性**（你可以引导或纠正 AI）会容易得多。Agent 则需要更加小心地设计透明性，例如记录思维过程，也需要加入诸如限制条件、人工介入等控制机制。

不过，如果设计得当，agent 依然可以被做成**足够可观测、足够安全**，以满足实际使用要求。关键在于：不要把 agent 当作一个永远正确的黑箱，而是要给它装上足够的报告与干预钩子。一个经验法则是：如果你发现自己很难解释某个 AI 系统为什么做了某个决策，那通常意味着你需要增加更多可观测性，例如让 agent 解释自己，或者直接降低它的自主性。

## 结论与最佳实践

AI workflows 与自主 agents 都是 AI 开发者工具箱中的重要工具。Workflow 带来的是**简单性、可靠性与清晰性**：当你知道应该做什么，只是想让 LLM 按步骤完成时，它非常适合。Agent 带来的是**适应性与能力上限**：它可以处理那些无法被整齐画成流程图的问题，因为它能自己寻找路径。

真正的选择取决于问题语境：要用*“适合你需求的系统”*，而不一定是最复杂、最炫的系统。很多时候，最好的做法是从最简单的方法开始，甚至只是单一 prompt；只有当简单方案不够时，再升级成多步 workflow，或者进一步演化为完全自主的 agent。

对于确实需要 agentic 系统的场景，Anthropic 的经验给出了几条值得重复强调的最佳实践：

* **尽量保持设计简单。** Prompt、工具集、逻辑结构越复杂，失败模式越多。目标应该是：用尽可能少的工具和尽可能直接的推理步骤，完成任务。
* **让 agent 的推理过程可见。** 在开发阶段，甚至在生产中的审计场景下，都应该让 agent 展示自己的计划与思考过程。这会显著提升调试效率，也有助于建立信任，因为你能更早发现问题。
* **重视 agent 与计算机之间的接口，也就是工具。** 工具定义本身就是 prompt engineering 的一部分。它们应当尽可能易于模型理解和调用，包括清晰文档、示例，以及避免让模型困惑的格式。像做人机界面测试一样去测试工具，并持续优化它们。
* **实施护栏，并进行严格测试。** 在把 agent 真正放到生产环境之前，必须先在沙箱场景中做测试，配合自动评估，并设置明确的硬限制，例如时间上限、迭代上限、成本上限等。对于关键动作，还必须有 fail-safe，例如强制人工确认，以防止自主循环造成意外后果。

从本质上说，构建有效的 LLM 系统，就是在**简单与复杂**、**控制与自主**之间做平衡。Workflow 与 agent 正是这个平衡光谱上的两个位置。理解它们在设计意图、架构、灵活性、使用场景、开发代价与控制方式上的差异，能帮助开发者更理性地决定哪种方法，或哪种混合方案，更适合自己的应用。

而无论你最终采用哪种方法，都应持续**测量效果并不断迭代**。基于真实世界反馈对系统持续打磨，是把一个不错的原型变成真正稳健解决方案的关键。

归根到底，成功来自于为问题选择正确工具：有时一个直接的 workflow 就够了，有时只有自主 agent 才能胜任。只要遵循上述原则，并结合行业里的实战经验，AI 开发者就能同时利用这两类范式的优势，构建既强大又可靠的系统。
