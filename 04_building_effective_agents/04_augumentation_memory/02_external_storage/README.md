# 面向 AI Agent 的长期记忆：向量数据库 vs 关系型数据库 vs 知识图谱

## AI Agent 中的长期记忆

AI Agent，例如基于 OpenAI Agents SDK 构建的 Agent，需要长期记忆来在多次会话之间保留并召回信息。如果没有持久化记忆，Agent 会忘记之前的交互，进而表现出重复、割裂或不一致的行为。长期记忆让 Agent 能像人类一样记住事实、用户偏好和过去事件。

实现这类记忆的常见方案包括 **向量数据库**、**关系型数据库** 和 **知识图谱**。这三种方式各有不同的优缺点，适用于 Agentic AI 记忆系统中的不同需求。

## 用向量数据库做记忆

向量数据库会把数据，例如文本、图像等，表示为高维向量（embedding），并在向量空间中执行相似度搜索。这是一种非常常见的 *语义记忆* 实现方式，也经常用于检索增强生成（RAG）系统。Agent 不再依赖关键词匹配，而是通过对查询做 embedding，并找到最相近的向量，从而召回语义相关的信息。

**优点：**

* **适合非结构化数据：** 向量存储可以为文档、图像、音频等多种非结构化数据建立索引。这使它非常适合保存从自由文本或多媒体内容中抽取出来的知识。
* **支持语义相似度搜索：** 向量检索是基于含义找相关信息，而不是只看词面是否一致。这样 Agent 可以回忆出与当前问题在概念上相关的事实或片段，在很多场景下比简单关键词搜索更强。
* **适合 RAG 大规模扩展：** 很多现代 AI 应用会使用像 FAISS、Pinecone、Weaviate 这类向量数据库来存储成千上万甚至数百万条 embedding。这类系统通常对高维空间中的 *k* 近邻检索做了优化，因此可以在大型知识库中快速取回上下文。

**缺点：**

* **容易丢失上下文和关系：** 数据在被切分成独立向量后，原始上下文或信息顺序可能会丢失。向量相似度检索只会返回语义上“最接近”的内容，却无法理解它们之间的逻辑关系或时序关系。比如，某个用户过去喜欢 *Brand A* 的鞋，但后来改为 *Brand B*。如果只用纯向量搜索，系统可能因为语义相似，仍然召回旧的“喜欢 Brand A”这条信息，而忽略后来偏好已变化。这说明当上下文没有被编码进记忆系统时，向量记忆很容易召回过时或因果上错误的信息。
* **没有原生的时间或因果模型：** 向量本身不具备时间或因果概念。它们只是空间中的点，没有显式连接。因此，仅依赖向量记忆的 Agent 很难处理**时序问题**，例如某件事是先发生还是后发生，或者多个事件之间的因果关系。这类方法对“信息如何随时间演化”的追踪能力很弱。
* **可能出现不准确召回：** 相似度检索依赖数值距离，因此 embedding 存储有时会召回一些虽然主题相近、词汇相关，但实际上并不能回答问题的片段。重要细节可能会被混淆或遗漏。例如，曾经有向量数据库因为 chunk 接近，返回 “1983” 而不是 “1984”，从而错误回答 Macintosh 首次发布年份。这类 **garbage-in, garbage-out** 问题会直接误导语言模型。
* **扩展与更新成本高：** 存储和搜索非常大的向量集合会消耗不少资源。高维数据还会遭遇 *维度灾难*，数据规模变大后会拖慢搜索效率。而且，一旦新增数据，往往还要重新计算 embedding 或重建索引，这在大规模场景下成本很高。对于企业级记忆系统，这类性能与成本问题会更加明显。

*总结：* 向量数据库**实现简单**，在面向非结构化数据的语义检索场景中表现很强。它为 Agent 提供了广泛的联想式回忆能力。但它**忽略结构**，也不知道知识片段之间是如何关联、如何随时间变化的。这会在长期记忆使用上造成错误，例如召回已经失效的事实。因此，通常需要补充时间元数据、过滤器或搭配其他技术，来缓解这一类问题。

## 用关系型数据库做记忆

关系型数据库会以带有预定义 schema 的结构化表格来存储数据，也就是按行和列组织。它是传统应用中最经典的持久化方案，也可以作为 AI Agent 的一种记忆形式，尤其适合保存定义清晰、结构稳定的信息，例如用户资料、配置、日志等。

**优点：**

* **结构清晰、技术成熟：** 关系型数据库会强制 schema、字段类型和约束，这对于保存结构稳定的事实信息非常有用，例如用户 ID、计数器、偏好配置等。由于数据结构清楚，数据很容易分类，也能用 SQL 高效查询。关系型数据库已经是行业标准很多年，优势在于可靠性、安全性和 ACID 特性。基于 SQL 实现的 Agent 记忆，也会天然继承这些能力。
* **适合固定查询与事务更新：** 如果 Agent 的记忆场景包含频繁更新或事务操作，例如事件日志、用户信息更新等，关系型数据库处理得很好。它擅长基于索引进行结构化查询。例如，通过主键查找某个用户最近一次交互，在关系型数据库里就是最简单的用例。在 **OpenAI Agents SDK** 场景下，关系型数据库很适合保存**稳定事实**或系统配置，例如用户画像、很少变化的基础知识等，让 Agent 能够快速按需取回。
* **易于使用与集成：** SQL 非常普及，大多数开发者都已经熟悉它以及相关工具。把 Agent 数据写入关系型数据库，再在后续查询，是非常直接的做法。这使得关系型数据库成为满足基础记忆需求的一种**易于落地**的方案，尤其是在数据天然可以按表格组织时。

**缺点：**

* **Schema 固定，灵活性差：** 关系型数据库最大的限制，就是它依赖预先定义好的 schema。所有数据都必须符合固定表结构和外键关系，这会**限制数据组织方式**，而一旦 schema 需要变化，调整又比较重、也容易出错。但 Agent 的记忆需求通常会演化，例如新增实体类型、新增关系类型，这时改动 SQL schema 往往代价很高。对于丰富、多变、持续演化的知识，这种刚性会成为问题。
* **不擅长复杂关系表达：** 关系型表可以通过外键和 join 来“间接表示关系”，但关系本身不是一等公民。要表达多对多关系、动态网络化关系或复杂因果链条，往往需要额外设计中间表或非常复杂的 schema。对于需要推理“概念之间如何连接”或“事件如何互相影响”的 Agent 来说，这样的 SQL 查询会变得越来越难维护。更关键的是，关系型数据库**缺乏对关系随时间演化的原生支持**。像“用户 X 的偏好在过去一个月里是如何变化的”这类问题，除非你专门设计历史表和复杂查询，否则很难自然表达。这使得纯 SQL 很难承载**时间上下文**或因果链。
* **Join 成本和查询复杂度会上升：** 当知识规模变大时，尤其是涉及多表 join 或文本检索时，关系型查询性能会下降。如果想把每次对话轮次、每一条事实都放进标准化表结构里，那么按语义相关性或按时间线去查询相关子集，都会变得很麻烦。关系型数据库擅长事务型和结构化场景，但在**知识召回**这类任务上往往笨重，除非查询模式从一开始就设计得非常清楚。
* **缺少原生语义搜索：** 关系型数据库本身并不提供语义相似度搜索。默认查询通常是精确匹配或基础文本匹配。对于 Agent 来说，如果只依赖纯 SQL，它很难找出“与某个主题相关的所有事实”，除非你额外引入全文搜索扩展或 embedding 系统。因此，单独用关系型数据库，往往无法满足 Agent 对**模糊召回**或**概念召回**的需求。

*总结：* 关系型数据库**可靠、结构化强**，非常适合保存定义明确的事实或状态，例如用户 ID、计数器、配置等。如果记忆可以被很好地表格化，它是一种很稳妥的方案。但它**不天然适合复杂且持续演化的知识**。由于缺少灵活性，也很难自然承载丰富关系和语义相似性，所以它不适合作为 Agent 长期记忆的唯一方案。很多时候，关系型存储会和其他方案一起使用，例如用 SQL 保存主键和元数据，再用向量库或图存储负责更丰富的上下文。

## 用知识图谱做记忆

知识图谱会把信息表示为**实体（节点）**和**关系（边）**构成的网络，并通常附带语义信息。这类系统通常基于图数据库实现，例如 Neo4j 或 RDF 三元组存储。它的思想接近人类组织知识的方式，也就是按关系和层级来组织。对于 AI Agent 来说，知识图谱可以成为一种**丰富且结构化的记忆系统**，不仅能存储事实，还能存储事实之间的关系、含义，甚至时间变化。

**优点：**

* **原生存储关系：** 与关系型数据库不同，知识图谱会把关系作为数据模型的一部分显式存储，每条边都是一等公民。这意味着 Agent 的记忆天然会保留“事物之间如何连接”的网络。例如：*Person X* → *works at* → *Company Y*。这种连接本身就是推理的重要上下文。图数据库非常强调关系：它通过直接指针来表示实体之间的连接。对 AI Agent 来说，这意味着它可以顺着这些连接去*遍历*自己的记忆，而不会失去上下文链条。
* **灵活且支持演化：** 知识图谱通常是无固定 schema 或弱 schema 的。你可以随时新增节点类型或边类型，而不必像关系型数据库那样整体改 schema。这种灵活性非常适合长期记忆，因为 Agent 的知识体系会持续增长、变化。只要出现新的实体或新的关系类型，都可以自然接入。不会因为数据“不适合表结构”而被迫丢失信息。
* **语义和上下文能力强：** 知识图谱可以给节点和边加类型、属性、本体（ontology）等语义元信息，从而形成更深层次的上下文理解。它“更接近人类的思维方式”，不是只看数值距离，也不是只看固定表结构，而是以关系和语义为中心。这意味着 Agent 不只是按文本相似度取信息，还能进行图推理。例如，它能识别两个事实是否冲突，因为它们关联到了同一个实体；或者根据图上的连接关系推导出新的信息。知识图谱的结构化特性也带来了**可解释性**，因为你可以看到系统是通过哪些节点和边得出某个结论的，这对于调试和建立信任都很重要。
* **适合建模时间与因果：** 对 Agent 记忆来说，知识图谱最强的一点是它可以很自然地扩展为**时序知识图谱（Temporal Knowledge Graph, TKG）**。只要为边加入时间戳或有效区间，图谱就能表示事实随时间的变化。例如：*User A –\[liked]→ Product X（2023 年 1 月到 2024 年 3 月）*，然后变成 *User A –\[liked]→ Product Y（2024 年 4 月至今）*。这种时间粒度让 Agent 可以准确回答“用户去年的偏好是什么，现在又是什么”。它为 Agent 引入了向量库和普通关系型表都很难天然支持的时序感与因果感。一个设计良好的知识图谱，能让 Agent 的记忆**自带上下文、因果和演化能力**。那些会让向量库出错的例子，例如鞋子偏好的变化，在图谱里就很容易表达：旧的 “喜欢 Adidas” 关系可以在 “鞋子坏了” 事件后标记为失效，而当前生效的是 “喜欢 Puma”。这更接近人类记忆的工作方式，人类记住的不只是事实本身，还有事实发生的顺序以及因果联系。
* **查询能力强，支持多跳推理：** 借助图查询语言，例如 Cypher 或 SPARQL，Agent 可以对知识图谱执行复杂查询，并取回一小片与任务相关的子图。例如，它可以问：“找出过去 6 个月里与 Person X 一起参与过 Project Y 的所有同事。” 这种查询在 SQL 里可能会非常繁琐，但在图数据库里却很自然。Agent 可以利用这种查询方式更精确地取回任务需要的信息，而不是像向量检索那样只能模糊召回。更进一步，多 Agent 或多个进程还可以共享同一个知识图谱，把它作为一个**共享记忆底座**，并通过版本控制和来源追踪来支持协作。这使知识图谱成为多 Agent 系统里维护长期状态与一致性的强基础设施。

**缺点：**

* **搭建和维护复杂：** 相比向量库或关系型数据库，知识图谱的实现复杂度高得多。它需要认真思考**数据建模和 ontology 设计**，也要求团队对图数据库和语义建模有一定经验。要构建一个真正有用的 ontology，定义好实体类型、关系类型、约束，甚至结合 RDF/OWL 等语义标准，前期投入很大。而且随着数据变化，维护知识图谱也不容易：你需要持续更新、合并和纠正新信息，又不能破坏原有一致性。这种复杂度往往意味着需要专门团队持续维护，也正是为什么知识图谱虽然强大，却没有在所有 AI 项目中大规模普及。简单说，它的**开发门槛和维护成本都偏高**，对于小项目或早期项目来说，可能显得过重。
* **性能与扩展性需要认真设计：** 图数据库在沿已知关系做遍历时表现很好，但随着图规模增大，某些查询也会变慢。查询本质上是在图中遍历节点和边，如果 Agent 的知识图谱扩展到了数百万节点和边，那么除非做了足够优化，否则性能会逐渐下降。例如需要索引、限制遍历深度等。一些资料也指出，在非常大或高度稠密的图上，图数据库可能遇到效率问题。某些涉及大范围模式匹配的复杂查询，也可能不如经过良好索引优化的关系型数据库高效。虽然现代图数据库在很多实际场景里已经有不错扩展性，但如果把它用作不断增长的 Agent 记忆，性能调优会是必需工作。
* **工具与人才储备不如 SQL 普及：** 相比 SQL，知识图谱的开发生态和人才储备都更小。熟悉 SPARQL 或 Cypher 的工程师，显然少于熟悉 SQL 的工程师。这会导致开发和调试成本增加。此外，知识图谱接入 LLM 往往还需要额外桥接层，例如把自然语言转换成图查询，或者让 LLM 理解图查询返回的结构化结果。虽然这不是图技术本身的缺陷，但它确实意味着更高的**开发投入**，以及如果处理不好，还可能引入更高响应延迟。
* **数据接入成本高：** 知识图谱通常需要从非结构化数据中抽取结构化事实，例如用 NLP 去识别文本里的实体和关系。这个 ETL 过程往往复杂而且容易出错。如果源数据不完整或很噪声，图谱也会出现不完整或不一致。换句话说，知识图谱的质量完全取决于喂给它的数据，它不会自动“补出”缺失连接。如果 Agent 所处环境非常开放，例如自由对话场景，那么如何设计一个有效 schema 并持续把 relevant facts 写入图谱，会是很费人力的工作。还有一个挑战是**一致性处理**，也就是如何处理冲突信息。高级实现会用时间戳事实和冲突解决规则来做，但这又会继续增加系统复杂度。

*总结：* 知识图谱是 AI Agent **表达能力最强、上下文最丰富**的一种记忆形式。它让 Agent 不只是*存储*事实，还能理解这些事实如何彼此关联、如何随时间变化，以及如何共同构成更大的知识结构。这使它在长期 Agent 记忆场景中非常强大，因为 Agent 可以基于自己的经验和知识进行更接近人类的推理，借助图结构避免上下文丢失与事实矛盾。它的代价在于：**构建和维护复杂度高**，在超大规模数据上也可能引入性能成本。如果场景只需要快速、简单的检索，它未必是最划算的方案。对很多团队来说，更实际的路径是把知识图谱和其他技术结合使用，例如图负责结构化记忆，向量索引负责原始文本的语义搜索，从而在能力和工程成本之间取得平衡。

## 哪种方式最强？

如果站在 AI Agent 长期记忆的角度来比较，**知识图谱在表达能力和整体能力上是最强的方案**。一个设计良好的知识图谱，可以原生表示**语义关系、时间演化和丰富上下文**，而这正是向量数据库和关系型数据库都很难自然表达的。也就是说，由知识图谱支撑的 Agent，记住的不只是“事实本身”，还包括这些事实之间的联系和历史变化。这会直接带来更连贯、更智能的行为，例如理解偏好已经变化、知道一个事件如何导致另一个事件、避免和自己之前学到的内容冲突。知识图谱非常接近人类式记忆结构，自带因果、上下文和推理能力。

相比之下，**向量数据库**非常擅长从非结构化信息中做大范围召回，也**很容易部署**，但它对上下文和时间顺序没有真正理解。它在处理原始知识，例如文档、笔记、聊天记录时很有价值，但它的能力边界基本停留在“语义相似”这一层。Agent 虽然可能召回相关片段，但仍然需要自己重新推断这些片段之间的关系和时间顺序。**关系型数据库**则在结构化数据和可靠性方面表现很好，适合定义清楚的数据查询，但在长期记忆场景里**能力范围有限**。它无法自然地承载流动、复杂、网络化的知识结构，除非投入大量人工 schema 设计。它很适合事务型场景，却不适合承担 Agent 的全部长期知识体系。

因此，如果把“最强”定义为：能支撑最丰富、最**有上下文感且可持续演化**的记忆，那么**知识图谱就是赢家**。它让 Agent 真正具备“把点连起来”的能力，不仅知道发生了什么，还知道这些事情之间如何关联、如何随着时间变化，以及如何支持复杂问题查询。也正因此，越来越多专家会说，*“知识图谱是 Agent 记忆的未来。”*

不过，也必须承认：**最好的实际方案往往是混合架构**。例如，一个系统可以用知识图谱保存结构化事实和关系，用向量索引负责语义搜索非结构化内容。事实上，很多领先实现，例如 Zep 的 **Graphiti** 或 Neo4j 的混合检索，都是在图和向量之间互补，用 embedding 强化图查询，反过来也用图结构提升召回上下文的准确性，从而同时获得**深度上下文理解**和**广覆盖语义召回**。

一个真正高级的 AI Agent，通常会采用这种混合架构：

- 一个 **关系型数据库** 用于保存自身配置和显式用户数据，例如用户 ID、权限、用户明确表达过的偏好。
- 一个 **向量数据库** 用于索引其过往交互和学习材料的语义表示。
- 一个 **知识图谱** 用于综合这两类信息，构建实体，例如人物、地点、主题，以及它们之间关系的显式地图，从而支撑更深层的推理与上下文理解。

总结来说，如果你要的是一种真正适合 **Agentic 长期记忆** 的核心表示方式，那么**知识图谱**，尤其是带时间维度的知识图谱，提供了最强的能力。它让 AI Agent 能记住“谁、什么、何时、如何、为什么”，而不仅仅是召回零散事实。向量数据库和关系型数据库各自也有很适合的细分场景，前者擅长非结构化搜索，后者擅长结构化数据，但它们更适合作为互补工具，而不是单独承担 Agent 的长期记忆全部责任。一个以知识图谱为核心，并适度结合向量检索的 Agent，会更有能力从历史中学习，并在长期运行中保持智能和一致性。

**参考说明：** 上述分析基于近期关于 AI 记忆架构的研究与行业观点，包括向量数据库与图数据库的比较、时序知识图谱在动态记忆中的作用，以及这些系统在实际 Agent 场景中的应用经验。总体共识是：向量库和关系型表各自都有价值，但如果只看复杂、长期、可演化的 AI 记忆，知识图谱拥有**最强的表达能力**。
