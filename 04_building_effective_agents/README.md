# 构建高效的 AI Agent

https://www.anthropic.com/engineering/building-effective-agents

> 这篇文章的核心观点是：高效 Agent 不是靠复杂框架堆出来的，而是靠简单、可组合的模式逐步演进出来的。
>
> 一句话总结：先用最简单的单次 LLM 调用解决问题；只有当效果不够时，才逐步升级到 workflow，再升级到真正的 autonomous agent。
>
> **文章主线**
>
>   Anthropic 先区分了两类系统：
>
>   - Workflows：流程路径是代码预先写好的，LLM 只是其中一个步骤。
>   - Agents：LLM 会动态决定下一步做什么、调用什么工具、如何推进任务。
>
>   它的核心立场很明确：很多场景根本不需要 agent。如果单次调用加上检索、示例、少量工具就够了，就不要引入更高成本、更高延迟、更多错误累积风险的 agent 系统。
>
>   **5 种常见模式**
>
>   文章把生产里常见的 agentic 模式拆成几类，从简单到复杂：
>
>   1. Augmented LLM
>      带检索、工具、记忆的 LLM，是所有系统的基础模块。
>   2. Prompt Chaining
>      把任务拆成固定顺序的多步，每一步输出作为下一步输入。
>      适合：任务能稳定拆解、希望用更多步骤换更高准确率。
>   3. Routing
>      先分类，再把请求路由到不同 prompt、工具或模型。
>      适合：问题类型差异明显，比如客服分流、大小模型分流。
>   4. Parallelization
>      并行处理，分两种：
>      
>        - sectioning：把任务拆成独立子任务并发做
>      
>        - voting：同一任务做多次，再聚合结果
>          适合：提速，或提高置信度与鲁棒性。
>      
>
>   5. Orchestrator-workers
>      由一个编排者动态拆任务，再分给多个 worker。
>      适合：子任务在执行前无法预知，比如复杂代码修改、多源搜索分析。
>   6. Evaluator-optimizer
>      一个模型生成，另一个模型评估并反馈，循环迭代。
>      适合：评价标准相对明确，且“改一版会更好”的任务，比如写作、翻译、复杂搜索。
>
>   Anthropic 对 Agent 的定义和建议
>
>   真正的 agent 适合这种问题：
>
>   - 步骤数事先很难确定
>   - 很难写死固定流程
>   - 需要模型边做边判断
>   - 可以从环境里持续拿到“真实反馈”
>     例如：工具返回值、代码执行结果、测试结果
>
>   它特别强调两点：
>
>   - Agent 的本质通常没那么玄，很多时候就是“LLM + 工具 + 循环”
>   - 真正难的部分不是 loop，而是工具设计、工具文档、停止条件、人工介入点、测试和护栏
>
>   **3 条落地原则**
>
>   文章结尾给了三条最关键的原则：
>
>   1. 保持简单
>      不要为了“看起来像 agent”而做复杂系统。
>   2. 保持透明
>      最好显式展示 agent 的计划和中间步骤，方便调试和建立信任。
>   3. 认真设计 ACI
>      ACI 就是 Agent-Computer Interface，重点是工具接口要清晰、文档要明确、测试要充分。
>
>   Appendix 里最实用的部分
>
>   附录里给了两个特别适合 agent 的场景：
>
>   - 客服
>     因为既有对话，又要查数据、调工具、执行动作，而且成功标准相对清晰。
>   - Coding agents
>     因为代码可以通过测试验证，模型可以根据测试结果反复修正，反馈回路很强。
>
>   另外还有一个很实用的工具设计建议：工具格式要尽量贴近模型熟悉的自然文本形式，避免让模型输出难写、难维护的格式。比如别强迫模型生成很难精确维护的 diff 或复杂转义 JSON，除非确实必要。
>
>   这篇文章最重要的价值
>
>   它把“做 agent”从一种很容易被神化的概念，拉回到了工程视角：
>
>   - 不是先问“怎么做最强 agent”
>   - 而是先问“这个问题到底需不需要 agent”
>   - 再问“能不能先用最简单的 workflow 解决”
>   - 最后才是“如果要 agent，怎么把它做得可控、可测、可维护”

Anthropic 的《Building Effective Agents》一文对 Agentic AI 领域非常重要，因为它为设计和构建有能力、可靠的 AI Agent 提供了一个清晰且实用的框架。它将关注点从复杂、笨重、“什么都想做”的单体 Agent，转向基于可组合模式的、更模块化、更容易理解的方法。这是推动 Agentic AI 从研究概念走向工程实践的重要一步。

## 关键贡献与意义

下面是这篇文章的核心要点，以及它们为什么对 Agentic AI 的发展很重要：

* **区分 Workflow 与 Agent：** 文章明确区分了 **workflow**（预定义、顺序执行的任务流程）和 **agent**（动态的、具备决策能力的系统）。这有助于开发者为问题选择合适的方法。并不是每一个自动化任务都需要一个复杂的自治 Agent。这种区分能提升效率，并减少不必要的复杂性。

* **强调简单性与可组合性：** 文章最重要的观点之一是 **从简单开始**。它不建议一开始就依赖复杂、包罗万象的框架，而是倡导用更小、更易理解、可复用的组件或“模式”来构建 Agent 系统。这种方式能让系统更容易构建、调试和维护。

* **Agent 系统的基础模式：** 文章提出了若干构建 Agent 系统的关键模式。这些模式像乐高积木一样，为开发者提供了一套用简单模块拼装复杂 Agent 的工具箱。主要模式包括：
    * **Prompt Chaining（提示链）:** 一串连续的提示，上一步的输出作为下一步的输入。这是构建更复杂工作流的基础模块。
    * **Routing（路由）:** 一个 Agent 先对任务进行分类，再将任务分发给对应的子任务或专门的 Agent。
    * **Parallelization（并行化）:** 其中包含两个子模式：
        * **Sectioning（分片）:** 将任务拆分成相互独立的子任务，并行运行。
        * **Voting（投票）:** 对同一个任务运行多次，再聚合结果，以提高可靠性和准确性。
    * **Orchestrator-Workers（编排者-执行者）:** 一个中心化的“编排者” Agent 负责拆解复杂任务，并把子任务分配给专门的“执行者” Agent。这是解决复杂问题的强大模式。
    * **Evaluator-Optimizer（评估者-优化者）:** 一个 Agent 负责生成方案，另一个 Agent 负责评估并提供反馈，推动方案迭代优化。

* **Agent-Computer Interface（ACI，Agent-计算机接口）：** 文章强调，AI Agent 与其工具之间需要一个设计良好的接口，例如 API、数据库、网页搜索等。就像人类用户需要良好的人机界面（HCI）一样，Agent 也需要清晰、稳健的 ACI 才能有效使用工具。这包括清晰的文档、明确的参数定义，以及充分的测试。

* **给开发者的实用建议：** 文章还给出了很具体的建议，例如：
    * 从最简单的方案开始，只在确有必要时再增加复杂度。
    * 谨慎使用过于复杂的框架，因为它们可能掩盖底层逻辑，使调试变得困难。
    * 充分测试和评估 Agent 的表现。

## 为什么这对 Agentic AI 很重要

Anthropic 文章中提出的原则和模式之所以重要，主要有以下几个原因：

* **可靠性与可预测性：** 通过将复杂任务拆分为更小、更明确的组件，可以更容易构建出更可靠、更可预测的 Agent。
* **可扩展性与可维护性：** 模块化方法使系统更容易扩展，也更方便独立维护和更新各个组件，而不影响整个系统。
* **降低 Agentic AI 的门槛：** 这篇文章提供了清晰、易理解的框架，让更多开发者无需成为复杂 AI 研究专家，也能构建较成熟的 AI Agent。
* **推动走向工程学科：** 它有助于推动 Agentic AI 从偏研究导向的探索，走向具有最佳实践和设计模式的工程化学科。

总之，Anthropic 这篇文章为任何想构建高效、实用 AI Agent 的人提供了一份基础指南。它对简单性、模块化和清晰设计模式的强调，是对这个领域的重要贡献，并且很可能会在未来多年持续影响 Agentic AI 的发展。

- [研究人员通过研究多 Agent 系统常见失败方式来改进它们](https://www.deeplearning.ai/the-batch/researchers-improve-multi-agent-systems-by-studying-how-they-tend-to-fail/?utm_campaign=The%20Batch&utm_content=339887220&utm_medium=social&utm_source=twitter&hss_channel=tw-992153930095251456)

> 这篇文章的核心意思是：提升多 Agent 系统，不只是换更强的模型，而是系统性研究它们“怎么失败”。研究者分析了 150 多次失败案例，整理出一套多 Agent 常见失败模式 taxonomy，然后据此修改 prompt 和多 Agent 结构，结果在数学和编程基准上都获得了提升。
>
> 文章提到的失败大类有 3 个。第一类是规格问题，例如 Agent 丢失角色定位、忘记上下文、没理解任务边界。第二类是Agent 之间不对齐，也就是协作和通信失败，比如该澄清时不澄清、该共享信息时没共享。第三类是任务验证不足，比如任务还没真正完成，系统就过早结束。它的关键洞察是：多 Agent 系统常常模仿人类组织，因此它们的故障模式也很像组织协作中的问题。
>
> 研究者据此做了两类改进。一类是改 prompt，比如显式加入“在最终回答前先完成验证步骤”。另一类是改组织结构，比如把原本的简单双 Agent 分工，改成“问题求解者 + coder + verifier”这种更清晰的三角色结构。结果上，摘要显示 AG2 在 GSM-Plus 上从 84.3% 提升到约 89%，ChatDev 在 HumanEval 上从 89.6% 提升到约 91.5%。
>
> 这篇文章最值得记住的结论是：多 Agent 的问题，很多不是单个 Agent 不够聪明，而是协作机制设计得不够好。所以优化方向应优先看角色定义、通信协议、澄清机制、验证机制，而不是只盯着模型本身。
>
> 根据摘要推断，这篇文章对工程实践的启发可以概括成 4 点：
>
>   - 给每个 Agent 明确角色和职责，减少职责漂移。
>   - 强制加入澄清和确认机制，不要默认 Agent 会主动提问。
>   - 在结束前做任务验证，避免“看起来完成了，实际上没完成”。
>   - 把多 Agent 系统当作一个组织来调试，重点分析协作失败，而不只是个体输出错误。

- [我们如何构建多 Agent 研究系统](https://www.anthropic.com/engineering/built-multi-agent-research-system)

> **核心结论**
>
> 多 Agent 系统适合那类开放式、路径不确定、可并行探索的任务，尤其是 research。Anthropic 的做法不是让一个 Agent 顺序搜索到底，而是让一个主 Agent 规划，再生成多个子 Agent 并行调查不同方向，最后汇总并补引用。文中称，这种系统在他们的内部 research eval 上，相比单 Agent Claude Opus 4 有明显优势。来源 (https://www.anthropic.com/engineering/multi-agent-research-system)
>
> 系统怎么工作
>
> Anthropic 用的是典型的 orchestrator-worker 架构：
>
>   - 主 Agent 先分析问题、制定策略，并把计划写入 memory，避免超长上下文被截断。
>   - 然后创建多个子 Agent，让它们分别去网页、Google Workspace 或其他集成里查不同子问题。
>   - 子 Agent 会边查边根据工具返回结果调整搜索方向。
>   - 主 Agent 收集结果后决定要不要继续派更多子 Agent。
>   - 最后交给一个专门的 Citation Agent 处理引用，把结论和证据绑定起来。来源 (https://www.anthropic.com/engineering/multi-agent-research-system)
>
> 文章特别强调：这和静态 RAG 不一样。RAG 是先取一批相似文本再回答；他们这个系统是动态搜索 + 动态拆分 + 动态收敛。
>
> **为什么多 Agent 有效**
>
> Anthropic 的解释很务实：多 Agent 很大一部分收益来自于把更多 token 花在正确的问题上，并且用多个独立上下文窗口并行探索。对 breadth-first 查询尤其有效，因为多个方向可以同时推进。文章还提到，在他们对 BrowseComp 的分析里，性能差异大部分可以由 token 使用量、工具调用数、模型选择来解释。来源 (https://www.anthropic.com/engineering/multi-agent-research-system)
>
> 但代价也很明确：
>
>   - token 消耗很高
>   - 多 Agent 成本显著高于普通 chat
>   - 不适合高度共享上下文、强依赖实时协作的任务
>   - coding 任务当前通常没有 research 那么容易并行化来源 (https://www.anthropic.com/engineering/multi-agent-research-system)
>
> **他们学到的 8 条 prompt / tool 经验**
>
> 文章里最有价值的是这部分工程经验：
>
>   1. 像 Agent 一样思考
>      直接观察 Agent 逐步执行，找出真实失败模式，而不是只看最终结果。
>   2. 教主 Agent 如何委派
>      子 Agent 的任务说明必须明确目标、输出格式、工具范围和边界，否则会重复劳动或漏项。
>   3. 让投入与问题复杂度匹配
>      简单问题不要乱开几十个子 Agent；复杂问题才扩大搜索预算。
>   4. 工具设计极其关键
>      Agent-tool interface 和人机界面一样重要。工具描述差，会直接把 Agent 带偏。
>   5. 让 Agent 帮你改 Agent
>      他们发现 Claude 4 很适合做 prompt/tool description 改进器，甚至能专门测试 MCP 工具并重写描述。
>   6. 先宽搜，再收窄
>      不要一开始就用过长、过细的查询词；先广泛探索，再逐步聚焦。
>   7. 引导思考过程
>      主 Agent 用 extended thinking 做规划，子 Agent 用 interleaved thinking 根据工具结果修正下一步。
>   8. 并行工具调用极大提升速度
>      主 Agent 并行开多个子 Agent，子 Agent 内部也并行用多个工具，复杂任务耗时最多能大幅缩短。来源 (https://www.anthropic.com/engineering/multi-agent-research-system)
>
> **评测怎么做**
>
> 他们认为多 Agent 不能只按“有没有走预设路径”来评估，因为不同 Agent 可能走不同但都合理的路径。所以评测重点放在：
>
>   - 结果是否正确
>   - 引用是否对应结论
>   - 是否覆盖了用户要求
>   - 来源质量是否足够高
>   - 工具使用是否合理
>
> 他们大量使用 LLM-as-judge，并且指出小规模 eval 应该尽早开始，不必等到几百条样本才动手。人工测试仍然必须保留，因为它能发现自动评测漏掉的边缘问题，比如偏爱 SEO 垃圾站而不是高质量来源。[来源](https://www.anthropic.com/engineering/multi-agent-research-system)
>
> **生产环境里的难点**
>
> 文章最后强调，Agent 系统和普通软件不同，小改动可能带来很大的行为变化。由于 Agent 是长时间运行、持续持有状态的，一旦中途失败，不能总是从头再跑，所以系统要能从出错点恢复执行，而不是简单重启。[来源](https://www.anthropic.com/engineering/multi-agent-research-system)
>
> **一句话总结**
>
> 这篇文章最重要的启发是：多 Agent 的关键不是“多开几个模型实例”，而是把并行探索、任务分解、工具设计、评测和恢复机制一起工程化。如果任务天然适合并行搜索，多 Agent 能明显胜过单 Agent；如果任务不适合并行，成本和协调复杂度可能不值。
