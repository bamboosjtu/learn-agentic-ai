# Agentic AI 技术栈

开发 AI agent 需要一套完整的技术栈，将各种组件整合起来，以实现自主、智能的行为。这个技术栈包含从基础模型到部署框架的多个层次，每一层都对 agent 的功能起着关键作用。在这个生态中，有两个值得关注的框架是 **CrewAI** 和 **LangGraph**，它们分别提供了构建和编排 AI agent 的不同方法。

### **1. AI Agent 开发栈概览**

AI agent 技术栈可以概括为以下几个关键层次：

- **模型服务（Model Serving）**：核心是大语言模型（LLM），用于处理和生成类似人类的文本。这些模型通常通过推理引擎提供服务，并以 OpenAI、Anthropic 等平台的 API 形式暴露出来。

- **存储（Storage）**：agent 需要能够存储和检索信息，例如对话历史和外部数据源。Chroma、Weaviate 和 Pinecone 等向量数据库通过高效的基于 embedding 的搜索和存储来支持这一点。

- **工具与库（Tools & Libraries）**：为了执行超出文本生成范围的任务，agent 会使用工具和函数。LangChain 这类框架提供了集成这些工具所需的基础设施，使 agent 能够执行动作并与外部系统交互。

- **Agent 框架（Agent Frameworks）**：这些框架负责编排各个组件，管理状态、工具执行和交互。CrewAI 和 LangGraph 是其中的代表，它们为 agent 开发提供了不同的方法论。

### **2. CrewAI：基于角色的多智能体协作**

CrewAI 的设计目标是促进基于角色的 AI agent 协作，使它们像一个统一整体那样工作。每个 agent 都会被分配特定角色、背景、目标和记忆，从而实现结构化且高效的任务执行。这个框架特别适合构建复杂的多智能体系统，例如研究团队或复杂问题求解单元。

**CrewAI 的关键特性：**

- **用户友好的界面**：CrewAI 提供直观的界面，使没有陡峭学习曲线的开发者也能快速上手。

- **与 LangChain 集成**：CrewAI 构建在 LangChain 之上，因此可以访问大量工具和模型，从而增强 agent 的能力。

- **高级监控与报告**：该框架包含用于跟踪任务进度和 agent 性能的工具，便于对 AI 驱动流程进行细致分析。

### **3. LangGraph：基于图的工作流编排**

LangGraph 采用图结构来定义和编排 agentic 工作流，把每个任务或函数看作图中的一个节点，并在循环工作流中执行。这种方法能对应用流程和状态进行精细控制，因此特别适合需要高级记忆能力、错误恢复以及 human-in-the-loop 交互的复杂工作流。

**LangGraph 的关键特性：**

- **与 LangChain 无缝集成**：LangGraph 与 LangChain 集成，可访问广泛的工具和模型生态。

- **支持多智能体交互模式**：该框架支持多种多智能体交互模式，便于开发协作型 agent 系统。

- **细粒度工作流控制**：LangGraph 基于图的方式允许对工作流进行详细管理，这对需要复杂编排的应用尤其有价值。

### **4. 对比分析：CrewAI vs. LangGraph**

CrewAI 和 LangGraph 都为 AI agent 开发提供了强大的解决方案，但各自优势不同：

- **易用性**：CrewAI 提供直观界面，便于开发者快速上手。相比之下，LangGraph 的图结构可能需要对图架构有更深入的理解，但它能提供更强的流程控制能力。

- **定制性与灵活性**：LangGraph 的设计允许高度定制，更适合复杂应用。CrewAI 虽然易用，但由于其偏意见化的框架设计，在定制方面可能会遇到更多限制。

- **集成能力**：两者都与 LangChain 集成，因此都能访问丰富的工具和模型。

### **5. 结论**

开发 AI agent 需要一套结构良好的技术栈，将模型服务、存储、工具和编排框架整合在一起。CrewAI 和 LangGraph 是这个生态中的两种不同路径，各自适用于不同的开发需求。理解它们各自的特性和能力，有助于开发者为具体应用选择最合适的框架，从而推动自主 AI 系统的发展。

## 材料1摘要

[必读：AI Agent 技术栈](https://www.letta.com/blog/ai-agents-stack)

Letta 这篇文章对“AI agents stack”的核心判断是：agent 技术栈已经和传统 LLM 技术栈明显分化，原因不是模型本身变了，而是 agent 引入了持久状态、安全工具执行、长期记忆、跨 agent 通信和可部署性这些新问题。文章把 2024 年末的 agent 生态概括为三层：`model serving`、`storage`、`tools & libraries`、`agent frameworks`，以及更上层的 `agent hosting / serving`。

### 文章强调的关键点

- **模型服务层**：agent 的底层仍然是 LLM，但模型可以通过闭源 API、开源权重服务或本地推理引擎来提供。文中点名了 OpenAI、Anthropic、Together.ai、Fireworks、Groq、vLLM、SGLang、Ollama 和 LM Studio 等典型选择。
- **存储层**：agent 不是无状态聊天工具，而是依赖持久化状态的系统。向量数据库和 Postgres/pgvector 这类方案用于保存对话历史、长期记忆和 RAG 数据。
- **工具层**：agent 之所以不同于普通 chatbot，是因为它能调用工具。工具调用通常依赖结构化输出和 JSON schema，而真正的工具执行必须在沙箱中进行，不能把安全性交给模型本身。
- **框架层**：框架要负责状态编排、上下文窗口构建、多 agent 通信、记忆管理以及对开放模型的支持。Letta 特别强调自己的“数据库驱动状态”设计，而不是依赖序列化后再恢复状态。
- **部署层**：文章认为 agent 最终会像服务一样部署到云或本地基础设施，通过 REST API 提供能力。和 LLM 服务相比，agent 服务更难，因为它同时要解决状态、依赖和安全工具执行问题。

### 对比文中立场

文章对 CrewAI、LangGraph、Letta 等框架的评价，不是简单说谁“最好”，而是强调不同框架在状态管理、上下文透明度、跨 agent 协作和部署路径上有不同取舍。它还指出，随着 agent 逐渐走向生产，框架之间真正拉开差距的地方会是部署工作流，而不只是“能不能做 agent”。

这篇原文最重要的补充是：agent 技术栈的重点已经从“会不会调用模型”转向“能不能把 agent 当成有状态服务长期运行”。这也是为什么存储、沙箱、记忆和部署会和模型本身同等重要。
